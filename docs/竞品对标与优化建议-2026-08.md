> 分析对象：`D:\Code\open\ydsz-micro` 全仓（main 主应用 + 8 业务子应用 + comm 共享包层 + micro-kernel 自研微前端内核）

## 一、现状结论（TL;DR）

**内核能力已达到甚至局部超越开源竞品**（importmap 依赖共享、SRI+CSP、马尔可夫路由预测、speculation-rules 均为竞品未覆盖的差异化点），**但工程化护栏严重滞后于内核能力**——CI 缺失、E2E 为空、业务应用近零测试、性能预算只停留在 README 文字。当前的瓶颈不在"功能不够"，而在"质量保障体系没有闭环"。

| 维度 | 现状评分（5 分制） | 一句话结论 |
| ---- | ---- | ---- |
| 架构 | 4.5 | 分层干净（@core→effects 单向）、importmap 三级共享策略、micro-runtime 防腐层设计成熟 |
| 功能 | 4.0 | 三沙箱+灰度+版本管理+消息总线齐备；JS 侧 SRI 与运行时多版本共存是缺口 |
| 性能 | 3.5 | 预测/预加载设施领先，但性能预算无 CI 强制、预加载命中率无数据回环 |
| 体验 | 3.5 | 骨架屏/错误降级 UI/主题语言同步齐备；DevTools 扩展偏薄、a11y 未落地 |
| 工程化 | 2.0 | **无 CI、e2e/ 空、全仓仅约 17 个测试文件、ADR 文档缺失** |
| 过度设计 | 存在 3 处 | 三沙箱并存、Markov 预测收益未验证、canary/registry 后端闭环未接 |

## 二、能力对标矩阵（micro-kernel vs 主流竞品）

| 能力 | ydsz micro-kernel | qiankun | wujie | micro-app | Garfish | Module Federation |
| ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| 加载方式 | ESM 直引 + manifest | HTML 入口 + UMD | iframe + webComponent | HTML + Custom Element | 动态加载 | 构建产物远程模块 |
| JS 沙箱 | 快照/Proxy/iframe 三档 | 快照/Proxy | iframe 天然隔离 | Proxy/with | 快照/Proxy | 无内建 |
| 依赖共享 | **importmap 三级策略（core/core-ui/all）** | externals 约定 | 共享 window 弱约定 | externals 约定 | 模块共享 | **运行时版本协商（最强）** |
| 预加载 | hover/idle/route/frequency + speculation-rules | prefetch 简单 | preload | prefetch | 预加载 | 无内建 |
| 路由预测 | **马尔可夫链转移概率** | 无 | 无 | 无 | 无 | 无 |
| 资源完整性 | SRI（CSS）+ CSP nonce | 无 | 无 | 无 | 无 | 无 |
| 灰度/版本 | version.json + canary 按 userId | 无 | 无 | 无 | 有基础 | **多版本共存** |
| 保活调度 | keep-alive + LRU + TTL + 内存压力 + 可见性 | 手动 | 保活模式 | 无 | 无 | 无 |

**差异化优势（保持并放大）**：ESM 原生直引（无 HTML 解析/UMD/eval）、SRI+CSP 安全链、马尔可夫预测 + speculation-rules、五维资源调度。
**落后项（需收口）**：MF 的运行时多版本共存与版本协商、声明式组件封装（`<micro-app>` Custom Element 式开箱体验）、生态/插件机制。

## 三、五维度分析与可落地建议

### 3.1 架构优化

**已达标（维持现状）**：
- 依赖方向干净：`comm/@core` 无一处反向依赖 effects（grep 验证，仅 1 处注释说明 semver 下沉史）
- 请求层 8/8 应用统一 re-export `@ydsz/shared-auth`（apps 下无 `axios.create` 泄漏），并发刷新去重在 `comm/effects/request/src/request-client/preset-interceptors.ts:103-200`
- micro-runtime 作为 seam/防腐层隔离内核 API 与子应用面，是正确的演进锚点

**建议项**：
1. **importmap 版本锁定（P1）**：`conf/vite-config/src/micro-shared-deps.ts` 用 `^3.5.17` 等 range 经 jspm generator 解析，无 lock 产物。不同时间生成的主/子 importmap 可能解析到不同 patch 版本 → 双 Vue 实例 → provide/inject 割裂。**落地**：构建时生成 `importmap.lock.json`（依赖名→精确版本+URL hash），CI 校验主子一致；manifest 加 `deps` 字段记录期望版本，loader 加载时校验。
2. **运行时多版本共存（P1）**：version-manager 目前是"单版本+切换"，对齐 MF 需支持同一应用 A/B 双版本并存（entry URL 带版本 hash 隔离），让 canary 分流真正可用（见 3.5 过度设计第 22 条的闭环前提）。
3. **manifest 签名（P1，安全差异化）**：JS 走 `import()` 无法附加 integrity（浏览器限制，竞品同样无解），当前 SRI 仅覆盖 CSS（`loader.ts` injectStylesheets）。**落地**：构建期对 manifest.json 做 HMAC/ed25519 签名，loader fetch 后先验签再加载，防"manifest 本身被篡改"；可选 Service Worker 拦截模块请求做哈希校验。
4. **micro-kernel 独立发布形态（P2）**：当前是 workspace 内部包；若计划开源对标，需补 dist 构建 + 独立版本号 + README 徽章，`.changeset` 先初始化（见 P0-5）。

### 3.2 功能增强

1. **DevTools 扩展增强（P2）**：`chrome/` 核心仅约 137 行（background/kernel-bridge/content-script）。对标 React DevTools / vite-plugin-inspect，补：沙箱状态实时面板、Markov 转移矩阵可视化、预加载命中率时间线、消息总线事件流。
2. **声明式子应用组件（P2）**：micro-runtime 已有 `define-sub-app` / `standard-props` 基础，补一个 `<MicroApp name="xxx" />` Vue 组件封装（对标 micro-app 的 Custom Element 与 Garfish 组件化），降低二方接入成本。
3. **i18n key 静态校验（P1）**：8 应用 × zh-CN/en-US 无静态检测，仅运行时 `missingWarn`。**落地**：`bash/gen-locales-check.mjs` 递归对比 langs 目录 key 集合差异，接入 pre-push。
4. **monitor 上报端点配置化（P0）**：`comm/effects/monitor` 的 `/api/v1/monitor/error`、`/api/v1/monitor/web-vitals` 硬编码（web-vitals.ts:36），跨环境部署（内网/云端）不可用。**落地**：endpoint 走 `initMonitor({ endpoints })` 注入 + `.env` 覆盖。
5. **a11y 落地（P2）**：`@axe-core/playwright` 已声明依赖但零用例（README/ADR-005 自认）。随 E2E 一起补主链路 axe 扫描。

### 3.3 性能提升

**已达标**：manualChunks 三分割、模块预载 link-hints（preconnect/modulepreload）、Speculation Rules eager/conservative 分档、路由级骨架屏（manifest.routes）、INP 采集。

1. **性能预算 CI 强制（P0）**：README 中 FCP/LCP/TTI 预算全是文字，`lighthouserc` 与 `test:perf` 不存在。**落地**：分两步——先接轻量 `size-limit`（主应用入口 gzip 预算，CI 阻断），再补 Lighthouse CI（preview 起静态服务采样 3 次）。
2. **预加载命中率数据回环（P1，关键）**：马尔可夫预测 + 4 策略预加载目前**没有任何数据证明有效**。**落地**：loader 记录 `predicted→hit/miss` 与 `preload 提前量(ms)` 指标入 monitor，按周对比 route 策略 vs markov 策略命中率，用数据决定去留（呼应 3.5 第 21 条）。
3. **内存压力检测升级（P1）**：`task-queue.ts` 依赖 `performance.memory`（非标准、已废弃，仅 Chromium）。**落地**：feature-detect 优先 `performance.measureMemory()`（Chrome 128+ 标准 API），保留现有计数启发式降级。
4. **产物重复检测（P1）**：importmap 外置后仍需守护"子应用产物不得再打包 vue/element-plus"。**落地**：`vsh check-bundle`（或 rollup-plugin-visualizer 断言）扫 dist 中共享依赖出现次数，CI 阻断。

### 3.4 体验改善

**已达标**：错误分级降级 + error-ui、keep-alive 页面缓存、主题/语言跨应用同步（use-theme-sync/use-locale-sync）、Token 自动刷新对用户无感。

1. **弱网/离线全局提示（P2）**：子应用加载失败有降级 UI，但网络层离线/网关不可达缺全局提示条。**落地**：monitor 已有 breadcrumb，补 `navigator.onLine` + fetch 连续失败的全局横幅。
2. **加载进度反馈统一（P2）**：骨架屏按路由分型，但首屏主应用→首个子应用的"接力"阶段无统一进度指示，补 top progress bar。
3. **Sourcemap 治理（P1）**：`upload:sourcemaps` 已有，需确保生产 nginx 不对外暴露 `.map`（`nginx.conf` 加 `location ~* \.map$ { deny all; }`），并验证上传目标访问权限。
4. **DevTools 面板与排障文档（P2）**：配套"常见故障→DevTools 查看路径"速查表，降低二方排障成本。

### 3.5 过度设计识别（裁剪/降级建议）

1. **三沙箱并存（建议收敛支持矩阵）**：项目定位是"同团队、统一构建链的同源子应用集群"（README 自述），该场景下 snapshot/proxy 已足够，iframe 沙箱（含 RPC、origin 白名单加固）当前无真实用例。**落地**：在 README/ADR 明确"iframe 沙箱 = experimental，仅跨域/不可信三方接入场景"，其新特性测试与维护优先级降档，避免 3 套沙箱同步演进的成本；等有真实异构接入需求再激活。
2. **马尔可夫预测收益未验证（建议数据驱动开关）**：8 个内部中后台应用导航路径短、规律强，frequency 策略可能已够。**落地**：按 3.3-2 采集命中率对比数据；若 markov 相对 frequency 提升 <10%，默认策略改 frequency、markov 降为 opt-in，保留代码但不默认承担复杂度。
3. **canary/registry 后端闭环未接（避免前端空转）**：canary-manager 按 userId 分流、version-manager、registry-adapter 前端侧齐备，但 registry.json 由本地脚本 `gen:registry` 生成，未接入真实发布流/配置中心。**落地**：短期在 README 标注"需部署侧提供 registry 服务端点"的前置条件；中期在 ydsz-cloud 侧提供 registry 版本接口，否则这套能力处于半空转状态。
4. **en-US 全量双语（建议分级）**：内网中文系统维护 8 应用 × 全量 en-US 的边际成本低但非零。**落地**：框架级（comm/locales、Element Plus/dayjs 语言包）保留双语；业务级 en-US 按需（有出海/外包场景的应用再补），配合 i18n 静态校验防漂移。
5. **不应裁剪的"看似复杂"项**：micro-runtime 防腐层、五维资源调度（keep-alive/LRU/TTL/内存/可见性）、错误分级降级——这三者均有明确场景与测试覆盖（`__tests__/unit/` 10 个 spec），属于合理投入，维持。
