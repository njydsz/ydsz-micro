三、架构优化 — 模块级状态与边界收敛

3.1 P0 appInstances 模块级 Map 应纳入 createKernel 闭包

现状：scheduler.ts L224 定义 const appInstances = new Map<string, AppInstance>() 为模块级。虽然 ManagerRegistry 在 _stop() 时清除，但在同一进程内创建两个 Kernel 实例（单元测试并行 / SSR 场景）时，第二个 Kernel 会看到第一个 Kernel 残留的实例。

建议：将 appInstances + maxKeepAliveApps + keepAliveTTL + keepAliveEnabled + keepAliveTimestamp 全部迁移到 createSchedulerFacade() 闭包中返回，createKernel 持有此 facade 而非调用模块级函数。

// 方向（非完整实现）
// scheduler.ts
export function createSchedulerFacade(): SchedulerFacade {
  const appInstances = new Map<string, AppInstance>();
  let maxKeepAliveApps = 5;
  let keepAliveTTL = 30 * 60 * 1000;
  let keepAliveEnabled = true;
  // ... 返回 { createAppInstance, getAppInstance, activateApp, ... }
}

// kernel.ts createKernel 闭包内
const scheduler = createSchedulerFacade();

收益：彻底消除多 Kernel 实例状态串扰；与 createKernel 的 P0-A2 设计原则完全对齐。

预估工期：2d（修改范围大但重构路径清晰）

现状：bootstrap.ts L248 L259 使用 (microRuntime as any)?.getApps?.() 和 (microRuntime as any)?.prefetch?.() 访问 MicroRuntime 接口未暴露的方法。这些是 kernel 内部的实现细节，不应从 bootstrap 直接调用。

预估工期：0.5d

3.4 P2 SandboxType 多重定义 — 类型收敛

现状：SandboxType 在 micro-runtime/types.ts L29 定义，scheduler.ts L70 通过 re-export 引用，但 sandbox-strategy.ts L44 使用字面量联合类型 'snapshot' | 'proxy' | 'iframe'。三处定义，未来新增沙箱类型需同步修改。

建议：sandbox-strategy.ts 的 SandboxStrategy.type 直接引用 SandboxType，确保单一事实源。同时将 createSandboxStrategy 的 switch 改为 Map 注册模式（支持运行时扩展）。

现状：kernel.ts L944 使用 (window as any).__MICRO_KERNEL__ = kernelApi，devtools-bridge.ts 读取时也是 any。这在 TypeScript strict 模式下会产生 warning。

建议：在 micro-runtime 中声明 declare global { interface Window { __MICRO_KERNEL__?: MicroRuntime; } } 全局类型扩展。

预估工期：0.1d

四、功能增强 — 能力对标与缺失补齐

4.1 P0 KernelErrorCode.SANDBOX_ERROR 未在任何路径抛出

现状：error-boundary.ts L46 定义了 SANDBOX_ERROR = 'SANDBOX_ERROR'，但全量源码搜索中无任何位置抛出此错误码。scheduler.ts 的 activateApp 中沙箱创建失败仅通过 mount() / cleanup() 的 try-catch 兜底，未显式包装为 SANDBOX_ERROR。

建议：在 activateApp L434-441（createSandboxStrategy）外层增加 try-catch，沙箱创建失败时抛出 new KernelError(KernelErrorCode.SANDBOX_ERROR, ...)。

预估工期：0.3d

4.2 P0 switchToApp 缺 abort 机制 — 快速连续切换时 deactivate 泄露

现状：kernel.ts switchToApp 使用 switchToken 实现令牌竞态保护，仅能丢弃异步结果，不能中止正在执行的 deactivateApp。用户快速连续点击 3 个菜单链接时，第 1 个的 deactivateApp（含 unmount + cleanup 沙箱）仍会在后台执行完毕，造成不必要的 CPU 开销和潜在的「旧 deactivate 与新 activate 插花」时序问题。

建议：为 deactivateApp 增加 AbortSignal 参数，switchToken 变更时通过 AbortController 通知 deactivateApp 尽早中止（至少中止沙箱 cleanup 之后的步骤）。

对标：React 18 Concurrent Features 的 interruptible rendering；qiankun 通过 queued-app 机制避免类似问题。

预估工期：1d

4.3 P1 主子应用 CSS 运行时隔离缺失

现状：仅依赖 PostCSS 构建期 CSS scoping + 容器 data-micro-app 属性。若子应用使用 :global 选择器、第三方库注入全局样式或遗漏 PostCSS 配置，样式泄露无法在运行时拦截。

建议：
(a) 短期：container 沙箱激活时注入 all: initial; font: inherit; 兜底重置（需 CSS 变量兼容）
(b) 中期：参照 micro-app 的 scopecss 模块，在运行时对子应用样式表做前缀隔离（[data-micro-app="xxx"] 前缀注入）
(c) 为 iframe 沙箱模式提供 sandbox: { css: true } 子选项，iframe 天然隔离 CSS

对标：micro-app 运行时 CSS scoping；wujie Shadow DOM 隔离；qiankun experimentalStyleIsolation。

预估工期：2d（短期方案）/ 5d（中期完整方案）

4.4 P1 子应用路由状态记忆（Page Cache）

现状：keepAlive 仅缓存 DOM 树与组件实例（keep-alive 附带 Vue keep-alive 的组件缓存），但列表中滚动位置、表单输入、展开/收起状态等在切换后需要子应用自行恢复。

建议：在 LifecycleExports 中扩展 serialize?() / hydrate?(state) 方法，子应用可选实现。内核在 deactivate 时调用 serialize 获取状态快照，activate 时通过 mountProps 传入供 hydrate 恢复。

对标：Vue KeepAlive 的 include/exclude；React Router 的 <Outlet context> 模式。

预估工期：1.5d

4.5 P2 子应用懒注册（运行时 addApp）

现状：registerApps 必须一次性注册所有子应用。虽然 registerAppsAsync 支持异步拉取，但注册后无法运行时动态追加（如插件市场动态安装的应用）。

建议：暴露 addApp(config: MicroAppConfig): void — 运行时追加单个应用，自动触发 manifest 预热、版本检查与路由重新索引。

对标：qiankun registerMicroApps 支持多次调用增量注册。

预估工期：0.5d

4.6 P2 iframe 沙箱统一消息通道（MicroBridge）

现状：iframe 沙箱的 globalState 桥接已建立（sandbox-strategy.ts L204-231），但子应用其他类型的跨 realm 通信（如调用主应用 API、RPC 等）需要子应用自行管理 postMessage。IframeSandboxStrategy 已有 callRpc / registerMainApi / onChildMessage 方法但未在调度器中以标准化方式暴露。

建议：在 mountProps 中注入 microBridge 对象，封装 send / call / on 三方法。

预估工期：1d

4.7 P3 嵌套微前端

现状：不支持子应用内再嵌入子应用（嵌套微前端）。当前 8 个子应用均为扁平注册。

建议：短期不投入。若未来需求出现，需在内核层面实现 MicroRuntime 接口的自引用能力（子应用内 createKernel() 使用独立 instance）。建议在接口层预留 parentKernelName 字段作为方向性研究。

五、性能提升 — 运行时与加载路径优化

5.1 P1 LRU 淘汰全量排序 → 最小堆

现状：scheduler.ts L763 cached.sort((a, b) => a.lastActivatedAt - b.lastActivatedAt) 每次 O(n log n)。当前 n <= 5，影响甚微，但 maxKeepAliveApps 增大到 20+ 后需要替换为 MinHeap。

建议：实现一个轻量的 BinaryHeap，按 lastActivatedAt 维护最小堆。或在 n ≤ 20 时仍用 sort，超出时自动切换 heap。

预估工期：0.5d（轻量，可延后至实际需要时）

5.2 P2 预加载并发控制的 Worker 模式微调

现状：kernel-helpers.ts runWithConcurrency 在 worker await 期间持有 items[index++] 引用，但 V8 GC 在 Promise pending 期间不会回收该引用。实际影响可忽略。

建议：在 await 前将 item 赋值给局部变量并置 null items[i]，明确释放引用。优先级低。

5.3 P2 globalState getGlobalState 浅拷贝 → 结构化克隆可选

现状：globalStateAPI.getGlobalState() 返回 { ..._globalState } 浅拷贝。当 State 包含嵌套对象（如用户权限码数组、主题 token 树）时，子应用可能误修改共享引用。

建议：增加 getDeepSnapshot() 方法（使用 structuredClone），供安全关键场景使用；保持 getGlobalState() 浅拷贝兼容。

预估工期：0.3d

5.4 P2 子应用 entry 动态切割 — 避免加载未使用的沙箱代码

现状：micro-kernel 当前所有沙箱代码（snapshot + proxy + iframe）打包在一起。若用户仅使用 snapshot 沙箱（默认），iframe 和 proxy 的代码仍被加载。

建议：将 proxy-sandbox 和 iframe-sandbox 改为动态导入（import()），仅在注册为对应沙箱类型时才加载。对 snapshot-only 场景可缩减 ~15KB（gzip）。

预估工期：1d

5.5 P3 KeepAlive 自适应上限 — 基于内存压力

现状：maxKeepAliveApps = 5 固定值。低配设备（4GB RAM）可能内存紧张，高端设备（32GB）可以缓存更多。

建议：在 setupVisibilityAutoRelease 中增加内存探测，根据 performance.memory 动态调整上限：

function adaptiveMaxKeepAlive(): number {
  if (!performance.memory) return 5;
  const ratio = performance.memory.usedJSHeapSize / performance.memory.jsHeapSizeLimit;
  if (ratio > 0.9) return 1;
  if (ratio > 0.7) return 3;
  return 5;
}

预估工期：0.5d

七、过度设计评估 — ROI 再审视

7.1 O1 马尔可夫链路由预测 — 建议增加自动降级

评估：当前实现完整（一阶转移概率 + 指数衰减 + 持久化 + 500 条上限 + 冷启动 fallback），但生产环境命中率尚未量化。若 PreloadManager.debugInfo().hitRate < 5%，意味着 95% 的预测预加载浪费了带宽和 CPU。

建议：在 kernel.start() 后增加自适应逻辑：若连续 3 天 hitRate < 5%，自动将 route prediction 降级为简单的「最近 N 次频率」模型。DevTools 展示当前使用的模型级别。

预估工期：0.5d

7.2 O2 Speculation Rules API — 双预定确认

评估：当前仅在 prefetchStrategy='eager' 时注入，与 idle 预加载可能双预定（即浏览器预取 + 内核加载两次）。

建议：在 Speculation Rules 注入前检查 PreloadManager.preloadCache 是否已有该 URL，若有则跳过。或给 Speculation Rules 增加 referrer_policy 限制。

预估工期：0.3d

十、总结

micro-kernel v4.2.0 的综合评估：在微前端运行时领域已达到国内一流水平（超越 qiankun / wujie / micro-app 的核心能力覆盖度），在路由预测、错误分类、DevTools 三个方向有业界独有的差异化创新。

本报告与前三次分析的差异：

  1. v4.0 分析提出的 23 项建议中，约 80%（18 项）已落地；
  2. v4.0.1 复审关注的 sandbox-strategy 闭环、ManagerRegistry 拓扑排序、CompositeDisposableManager、健康检查异步化已全部完成；
  3. 本报告基于实际代码深度审计，新识别出 12 个差距，包括 appInstances 闭包化（P0）、deactivate abort 机制（P0）、Sentry 零聚合的 SANDBOX_ERROR（P0）等关键问题；
  4. 相比三份历史分析，本报告更侧重当前代码的实际差距而非已解决的问题，并对过度设计项进行了 ROI 再评估。

最关键的 3 个行动项：

  1. appInstances 闭包化（N1）— 彻底消除多 Kernel 实例状态串扰风险，是 P0-A2 设计的最后一块拼图
  2. 核心路径单元测试补齐（N3）— 当前 ~15% 覆盖率是最大的工程质量风险
  3. CSS 运行时隔离（N5）— 对标竞品的最大功能缺口，需在运行时兜底
