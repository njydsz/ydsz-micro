## 一、总体结论

项目对云顶编码规范的**基建层执行度很高**，核心强制项基本达标；存在 **2 项 P0 缺口**（v-html 净化指令已建未落地、业务层裸 fetch）、**5 项 P1 问题**（命名规范系统性漂移、超长逻辑文件、生成文件豁免标注缺失、测试覆盖不足、v-for 索引 key）及若干 P2 优化点。

| 维度 | 结论 |
|------|------|
| 类型安全（第 3 章） | ✅ 基本达标 |
| 命名规范（第 2 章） | ⚠️ 系统性漂移（规范 vs 代码约定冲突） |
| Vue 组件规范（第 4 章） | ✅ 大体达标，个别项违规 |
| 性能规范（第 5 章） | ✅ 基本达标 |
| API 请求规范（第 6 章） | ⚠️ 1 处业务层裸 fetch |
| 安全规范（第 7 章） | ❌ v-html 消毒未落地（有工具无使用） |
| 状态管理（第 8 章） | ✅ 达标（未发现 Options 风格 store） |
| 路由规范（第 9 章） | ✅ 达标 |
| 错误处理与日志（第 14 章） | ✅ 基本达标 |
| 代码度量（第 15 章） | ⚠️ 3 个逻辑文件超 500 行 |
| 测试规范（第 17 章） | ❌ 覆盖率远未达标 |
| 构建与依赖管理（第 18 章） | ✅ 达标（pnpm + commitlint + lefthook + vsh 全套） |

## 二、合规良好项（实证通过）

1. **TS 严格模式全开**（规范 3.4）：
   `conf/tsconfig/base.json` 启用 `strict` / `strictNullChecks` / `noImplicitAny` / `noImplicitThis` / `noImplicitOverride`，且额外启用 `noUncheckedIndexedAccess` / `noUnusedLocals` / `verbatimModuleSyntax`，**超出规范基线要求**。

2. **`any` 使用极少**（规范 3.1）：
   - `apps/*` 业务代码仅 1 个文件 3 处：`apps/workflow-web/src/views/designer/components/DesignerCanvas.vue`
   - `main/*` 仅 2 处（`use-network-status.ts`、`use-tabbar-micro-sync.ts`）
   - `comm`（排除 shadcn-ui 豁免目录）仅 4 处，其中 2 处为测试文件
   - `@core/ui-kit/shadcn-ui` 豁免条款执行正常

3. **axios 收口正确**（规范 6.1）：
   直接 import axios 的代码仅存在于 `comm/effects/request/`（统一请求客户端本体），业务层零直用。`export * from 'axios'` 也收口在 request 模块内。

4. **Vue SFC 行数全达标**（规范 15.1）：
   全仓最大的 SFC 为 `IconPicker.vue` 810 行，无任何文件超过 1000 行红线。

5. **Pinia Store 无 Options 风格**（规范 8.1）：
   全仓未匹配到 `defineStore(x, { state/getters/actions })` Options 语法。

6. **裸 console 极少**（规范 14.5）：
   `apps/*/src` + `main/src` 业务层仅 3 处；`@ydsz/monitor` 已在部分模块接入。

7. **v-safe-html 消毒指令已建设**（规范 7.1）：
   `comm/effects/common-ui/src/components/safe-html/index.ts` 实现了 DOMPurify 式白名单消毒（标签白名单 + 协议校验 + 属性过滤），`main` 侧 `global-search.vue` / `command-palette.vue` 已接入并在 `app.ts` 全局注册。

8. **豁免注解机制已运行**（规范 6.1 例外条款 / 15.1 豁免条款）：
   `@infra-fetch` 注解在 micro-kernel（health-check / loader / version-manager / registry-adapter / canary-manager-core）、monitor（web-vitals / error-monitor-queue）、shared-auth（sse.ts）等基础设施层正确使用；`@data-file` 注解在 common-ui icons.ts 已使用。

9. **路由规范达标**（第 9 章）：
   路由组件动态导入懒加载（`component: () => import('#/views/...')`），守卫统一在 `router/guard.ts` + `access.ts` 组织。

10. **构建与提交链路完整**（第 18 章）：
    pnpm + `only-allow pnpm` 强制、pnpm-lock 提交、catalog 统一版本、commitlint（Conventional Commits）、lefthook、turbo 任务编排、自研 vsh 提供 `check-arch` / `check-circular` / `check-dep` 架构守护。

## 三、问题清单（按优先级）

### 🔴 P0-1：v-safe-html 指令已建未落地，5 处裸 v-html 继续暴露（规范 7.1【强制】）

指令源码注释明确写着 **"替代全局 5 处裸 v-html，防御 XSS"**，但实际只有 `main` 接入，`apps` 内 4 个文件 5 处仍是裸 `v-html`：

| 文件 | 位置 | 风险 |
|------|------|------|
| `apps/nextwiki-web/src/views/search/index.vue` | `<span v-html="item.highlight ...">` | **最高**：内容来自搜索接口返回（`highlight: true` + 自定义 PreTag/PostTag），服务端数据注入面 |
| `apps/workflow-web/src/components/FlowDiagram/index.vue` | ×2 处 `v-html="svgContent"` | SVG 来自流程渲染，若含外部数据需消毒 |
| `apps/workflow-web/src/views/instance/components/FlowDiagramViewer.vue` | `v-html="diagramSvg"` | 同上 |
| `apps/literule-web/src/views/dsl/components/DslEditor.vue` | `v-html="highlightedHtml"` | DSL 高亮拼接 HTML |

**修复动作**：子应用入口统一注册 `v-safe-html`（可挂到 comm 层共享 setup），将上述 5 处替换为 `v-safe-html`；白名单需补充 `em` / `svg` 场景（或对 SVG 场景单独走属性消毒）。

### 🔴 P0-2：业务层裸 fetch 无豁免注解（规范 6.1【强制】）

- `apps/nextwiki-web/src/views/file/file-preview.vue`：`await fetch(\`/api/v1/nextwiki/download/${props.fileNode.id}\`)`
- 这是业务视图层代码，不属于基础设施层例外；且未带 `// @infra-fetch` 注释。

**修复动作**：改走 `requestClient`（二进制场景用 `responseType: 'blob'` 或 baseRequestClient）；若确因下载流场景保留 fetch，必须补注解并说明理由。

### 🟡 P1-1：命名规范系统性漂移（规范 2.1 / 2.2 / 4.4【强制】）——需决策

代码现实与规范条文存在大范围冲突，**这不是零星违规，而是规范与脚手架约定的分歧**：

- 规范要求 Vue 组件文件 PascalCase，但仓库约 **250 个 .vue 文件**采用 kebab-case / `index.vue` 约定，PascalCase 仅约 20 个（且集中在 workflow/cronjob/designer 一侧），风格混杂。
- 目录命名存在 camelCase 违规：`apps/cronjob-web/src/views/jobDag`、`jobDagInstance`、`jobGroup`、`jobLog`、`apps/agent-web/src/views/agentChat`、`apps/system-web/src/views/dictItem`、`dictType` 等（规范 2.2【强制】kebab-case）。
- 混合命名残留：`dictItem-form.vue`、`jobDag-form.vue`（camel + kebab 混搭）。

**两条路线（需团队决策）**：
- **A. 修订规范**（推荐）：承认"kebab-case 目录 + kebab-case 组件文件 + index.vue 入口"为既定约定，将 2.1/4.4 改为 kebab-case；仅保留组件 `defineOptions({ name })` PascalCase 要求。理由：250 个文件的批量重命名收益低、git blame 断裂、与路由 views 约定强耦合。
- **B. 执行代码整改**：按子应用分批重命名（先改 camelCase 目录 7 处这个纯违规项，再统一文件名），配合 vsh 增加 check-naming 守护。

无论哪条路线，**camelCase 目录这 7 处属于明确违规，应先修**。

### 🟡 P1-2：业务逻辑文件超 500 行（规范 15.1【强制】）

| 文件 | 行数 | 说明 |
|------|------|------|

### 🟡 P1-3：生成 API 模型文件缺豁免标注 + 头部不一致（规范 15.1）

5 个 `apps/*/src/api/models.ts`（workflow 1831 / userinfo 1355 / literule 1263 / message 1187 / cronjob 1071 行）均超 1000 行纯类型文件上限，虽由 `bash/gen-contract.py` 生成（头部有 `auto-generated — DO NOT EDIT`），但：

**修复动作**：在 `gen-contract.py` 模板中统一生成头部（`/* eslint-disable */` + `// @data-file 纯类型生成件` + 生成命令说明），一次修改全部对齐，并执行 `gen:contract:check` 验证。

### 🟡 P1-4：测试覆盖严重不足（规范 17.1【强制】）

全仓（排除 node_modules）仅 **18 个测试文件**，且集中在 `comm/utils`、`micro-kernel` 等；8 个子应用（`apps/*`）几乎无测试。对照 17.1 "新增代码覆盖率 ≥ 70%、核心业务逻辑 ≥ 90%" 无法成立。

**修复动作**：
