> **版本**：1.0.0
> **日期**：2026-09-14
> **范围**：ydsz-cloud（后端 40 模块 / 4184 源文件）+ ydsz-micro（前端 40+ 包 / 773 源文件）
> **对标**：阿里 Cloud Native 全家桶、字节 ByteDance 微服务治理、美团 OCTO/Squirrel 体系、腾讯 TARS/TSF

## 二、能力贯通维度

### P0-1：测试覆盖率破零（后端）

**现状**：4184 个源文件仅 1 个 ArchUnit 测试类，核心引擎（workflow/literule/cronjob）无任何单元测试。对比阿里《 Java 开发手册》"单测覆盖率不低于 80%"红线、美团"核心服务单测门禁 75%"实践，属于阻断级负债。

**建议方案**：

1. **分阶段破零路径**（按 ROI 排序）

| 阶段 | 目标模块 | 测试类型 | 预计工作量 | 预期覆盖率 |
|------|---------|---------|-----------|-----------|
| Sprint 1-2 | literule domain（规则 DSL 解析、表达式求值） | JUnit 5 + Truth 断言 | 5 人日 | 该模块 60% |
| Sprint 3-4 | workflow domain（状态机流转、节点路由） | JUnit 5 + 状态机断言 | 6 人日 | 该模块 55% |
| Sprint 5-6 | cronjob domain（分片策略、异常重试） | JUnit 5 + Awaitility | 4 人日 | 该模块 50% |
| Sprint 7-8 | ydsz-common L1-L3 | JUnit 5 + 边界用例 | 3 人日 | 公共层 70% |

2. **基础设施配套**

- 引入 `spring-boot-starter-test` + `Testcontainers`（针对 Redis/MySQL/MinIO 集成测试）
- Maven Surefire 配置中设置 `<failureIfNoTests>true</failureIfNoTests>` 的模块白名单
- CI 流水线中引入 JaCoCo（`<minimum>0.60</minimum>`）作为质量门禁

3. **规范层面**：在《云顶编码规范》§15 测试规范中明确"D Domain 层新增方法须同步单测"的强制要求，YDIZ-TEST-001 设为 P0 级。

### P0-2：分布式事务按需落地

**现状**：ydsz-common-seata 模块已引入 AutoConfiguration + Properties，但 8 个业务模块中零 `@GlobalTransactional` 使用。对比阿里 Seata AT 模式在电商/金融场景的标准实践，跨服务数据一致性当前依赖"本地消息表 + Outbox 模式"的最终一致性方案，存在数据不一致时间窗。

**建议方案**：

1. **场景识别**：盘点 8 个引擎中的跨服务强一致性场景候选

| 候选场景 | 涉及引擎 | 建议模式 | 优先级 |
|---------|---------|---------|--------|
| 流程实例创建 + 任务初始化 | workflow → cronjob | Seata AT | P0 |
| 规则发布 + 灰度配置同步 | literule → message | Outbox 增强（现有） | P1 |
| 知识库文档创建 + 索引构建 | nextwiki → search | Outbox 增强（现有） | P1 |
| Agent 任务分发 + 结果聚合 | agent → message | SAGA | P2 |

2. **最小验证 PoC**：选择 workflow → cronjob 的"流程创建同时初始化定时任务"场景，实施 Seata AT 模式的端到端验证，确认：
   - TC（Transaction Coordinator）与 Nacos 注册中心的连通性
   - undo_log 表在各业务库的写入性能影响
   - 异常回滚对业务异常类型的覆盖正确性

3. **决策矩阵**：并非所有跨服务调用都需要强一致性。建议建立"一致性决策树"写入架构决策文档（ADR-010），避免 Seata 被滥用。

### P0-3：前端测试体系重建

**现状**：前端测试被规范§15.10 明令禁止，质量仅靠 ESLint/Stylelint/ArchUnit（vsh check-arch）静态检查兜底。对比字节 Web 框架团队" Vitest + Testing Library 测试覆盖率 ≥ 70%"、美团前端"子应用 CI 跑单元 + 快照 + E2E"的规范，存在系统化回归风险。

**建议方案**：

1. **技术选型**：Vitest（与 Vite 原生集成）+ @vue/test-utils + Playwright（E2E）
2. **规范修订路径**：

- 修订《云顶编码规范》§15.10 为"测试策略分层"：禁止无断言的纯渲染测试，鼓励行为测试
- 从 shared-business 包中的 `dict-select` / `excel-import` / `approval-timeline` 等高复用组件切入，补充行为测试
- 预期首期覆盖：20 个核心组件 × 平均 3 用例 = 60 测试用例

3. **基础设施**：在 turbo pipeline 中增加 `test` 任务，与 `lint` 并列作为 CI 门禁阶段

## 三、架构优化维度

### P1-1：Sentinel 业务侧限流熔断接入

**现状**：当前限流熔断仅配置在 ydsz-gateway（SentinelGatewayConfig），8 个业务引擎的 199 个 Controller 中无 `@SentinelResource` 或 `@RateLimiter` 注解。对比阿里 Cloud 架构"网关 + 业务侧双层防护"标准，存在级联故障风险。

**建议场景与接入方案**：

| 引擎 | 防护切入点 | 建议策略 |
|------|-----------|---------|
| agent | LLM 推理接口（长耗时） | QPS 限流 + 线程数隔离（防止推理打垮线程池） |
| workflow | 流程发起接口（写密集） | 集群限流 + 关联流限流（按租户维度） |
| message | 消息发送接口（资源消耗大） | 令牌桶限流 + 异步降级 |
| nextwiki | 文件上传/预览（IO 密集） | 连接数限制 + 排队策略 |

**接入路径**：

1. 在 ydsz-common-safe 模块中封装 `@RateLimit` 自定义注解，底层适配 Sentinel
2. 网关侧配置 SentinelGatewayConfig 做第一层粗粒度防护
3. 业务侧通过 `@RateLimit(resource = "agent:infer", qps = 10)` 做第二层细粒度防护
4. 熔断规则通过 Nacos/Apollo Sentinel DataSource 动态推送

### P1-2：可观测性告警闭环

**现状**：OpenTelemetry + SkyWalking 双通道已集成，Metrics（Prometheus）已采集，但告警规则（PrometheusRules/AlertManager）完全缺失。三要素"采集-展示-告警"中缺少最后一环。

**建议方案**：

1. **Rules 配置文件**（创建 `deploy/prometheus-rules.yml`）

```yaml
groups:
  - name: ydsz-service-health
    rules:
      - alert: YdszServiceDown
        expr: up{job=~"ydsz-.*"} == 0
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.instance }} 服务不可用"
          
      - alert: YdszHighErrorRate
        expr: rate(http_server_requests_seconds_count{status=~"5.."}[5m]) / rate(http_server_requests_seconds_count[5m]) > 0.05
        for: 3m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.uri }} 5xx 错误率超过 5%"

      - alert: YdsjSlowAPI
        expr: histogram_quantile(0.99, rate(http_server_requests_seconds_bucket[5m])) > 2
        for: 5m
        labels:
          severity: warning
```

2. **业务级 SLO 定义**（建议首批 3 个）

| 服务 | SLO | 测量方式 |
|------|-----|---------|
| Gateway 路由 | 99.95% 可用性 | up{job="ydsz-gateway"} |
| 流程引擎接口 | P99 延迟 < 500ms | http_server_requests_seconds |
| 消息发送成功率 | ≥ 99.9% | rate(message_send_total{status="success"}) / rate(message_send_total) |

3. **告警路由**：AlertManager 配置 → 企业微信/飞书 webhook（按 severity 分级：critical → 电话+消息，warning → 消息）

### P1-3：ydsz-agent 模块架构收敛

**现状**：agent 模块是近期变更最密集的引擎（9 月密集提交 50+），14 个控制器覆盖推理/记忆/编排/RAG 等多个关注点。按 DDD 分层理念，存在"胖 web 层"信号——复杂度快速膨胀但分层边界可能被突破。

**建议方案**：

1. **分层审计**：在下一个版本迭代前，对 agent-web 进行一次分层合规审查
   - 确认所有 LLM 调用/inference 编排逻辑位于 domain 或 server 层
   - 确认 web 层 Controller 不包含业务逻辑（仅做 DTO 转换 + 调用转发）
   - 确认 SSE 流式响应在 web 层处理，不在 domain 层泄漏响应式编程细节

2. **拆分候选**：如果 agent 模块在未来 3 个月内突破 20 个 Controller，考虑拆分为 `ydsz-agent-inference`（推理引擎）+ `ydsz-agent-orchestration`（编排引擎）两个微服务。

3. **ADR-011**：编写架构决策文档，明确 agent 模块的微服务拆分触发条件（如：团队规模 > 8 人、独立发布节奏需求、资源隔离需求）。

### P2-1：前端微内核 iframe 沙箱实战验证

**现状**：自研微内核 v4.4 已支持 snapshot/proxy/iframe 三种沙箱模式，iframe 标记为 experimental，无生产子应用接入。

**建议方案**：

1. **Pilot 选择**：选择 generator-web（纯工具型应用，无敏感数据交互）作为 iframe 沙箱试点
2. **验证清单**：
   - postMessage 通信延迟 < 50ms
   - 主子应用 CSS 完全隔离（ShadowDOM 兜底）
   - 主子应用版本独立升级互不阻塞
3. **成功后推广**：根据 Pilot 数据决定是否在 sandbox-enabled 子应用中默认启用 iframe 模式
4. **KPI**：沙箱隔离故障（子应用崩溃导致主应用白屏）归零

### P2-2：前端国际化语种扩展

**现状**：仅中英文两套语言包，未覆盖第三语种，无 RTL（Right-to-Left）支持。对比美团/字节出海产品"三语起步，RTL 预留"的规范，存在国际化天花板。

**建议方案**：

1. **第三语种储备**：根据目标市场选择日语或东南亚语（th/vi），优先覆盖 20 个核心页面的高频词汇
2. **RTL 预备**：在 Design Token 中使用逻辑属性（`margin-inline-start` 替代 `margin-left`），避免后续 RTL 适配大规模重构
3. **i18n 键值规范**：统一使用 `模块_页面_组件_动作` 命名规范（如 `workflow_form_submit_button`），避免语义重复
4. **extract-i18n 自动化**：CI 阶段运行 `npx extract-i18n --check` 比对 zh-CN/en-US 键值一致性，检测缺失翻译

## 四、功能增强维度

### P1-4：灰度发布全链路贯通

**现状**：网关层 `GrayLoadBalancer` 已实现标签路由，cronjob 模块有 `CanaryReleaseService` 做灰度策略管理，但全链路（前端 → 网关 → 服务 → 数据库）灰度染色未贯通。

**对比美团 LiteSET、阿里 MSE 灰度发布成熟方案**：

1. **灰度维度补齐**：

| 维度 | 当前 | 建议 |
|------|------|------|
| 用户/租户 | 无 | 基于 TenantContext 的 tenant_id % 100 分流 |
| 请求特征 | 无 | 基于 Header `X-Gray-Tag` 的前后端联动 |
| 地域 | 无 | 基于 gateway 的 `X-Region` 路由 |
| 版本 | 无 | 基于 `ApiVersion` Header 的版本亲和 |

2. **灰度发布控制台**（前端 + 后端联动）：
   - 新建 `gray-release` 管理页面，支持配置灰度规则（用户白名单/流量比例/Header 匹配）
   - 与 Prometheus 指标联动，展示灰度版本的核心指标对比（错误率/P99/业务成功率）
   - 支持一键回滚（Nacos 配置推送）

3. **实现路径**：
   - 后端：ydsz-common-traffic 新建模块，封装灰度路由逻辑
   - 前端：在 TenantContext 组件旁增加 `GrayReleaseBadge` 标识当前灰度状态
   - CI/CD：在发布流水线中增加灰度审批节点

### P1-5：智能引擎（Agent）生产就绪度提升

**现状**：ydsz-agent 具备 LLM 推理、RAG 检索增强、TeamRun 多 Agent 编排、SSE 流式响应、记忆管理、可观测等能力，架构最复杂但稳定性最薄弱。

**对标字节 Coze、阿里百炼、美团 LongCat 等平台**，建议加强以下能力：

| 能力 | 现状 | 建议 |
|------|------|------|
| Prompt 版本管理 | 未见版本控制 | 引入 Prompt Registry，支持 A/B 测试和版本回滚 |
| 模型路由 | 未见多模型切换 | 抽象 ModelRouter，支持主备模型自动 failover |
| 成本观测 | 无 Token 计费 | 集成 Token Usage Metrics，按租户/用户维度统计 |
| 安全过滤 | 未见输入/输出过滤 | 引入 Prompt Injection 检测 + 输出内容审核（对接 ydsz-literule） |
| 调试能力 | 有 ObservabilityController | 增强为 Playground（在线调试+历史回放+链路追踪可视化） |

**优先级排序**：
1. 成本观测（ROI 最高，直接影响商业化）
2. Prompt 版本管理（降低生产事故恢复时间）
3. 安全过滤（合规要求）

### P1-6：数据字典与规则引擎联动

**现状**：数据字典（system 引擎）与规则引擎（literule）目前独立运行。规则引擎的决策表中如果引用字典项，需硬编码 typeCode，字典变更后规则可能静默失效。

**建议新建 `DictRuleBridge`**：

1. 规则定义中支持 `${dict:dictType.code}` 语法引用字典值
2. 字典变更时（DictItem CRUD），自动触发关联规则的版本校验
3. 前端表单配置器中，规则决策表的枚举下拉可绑定字典类型

对比 Drools + Data Dictionary 集成方案，该能力属于"业务规则平台的高级特性"，能显著提升规则配置的灵活性。

## 五、性能提升维度

### P2-3：多级缓存架构优化

**现状**：已实现 Caffeine（L1）+ Redis（L2）多级缓存，Write-Through 装饰器，StripedLock 并发保护，TinyLFU 淘汰策略。缓存架构处于行业中上水平。

**进一步优化方向**：

1. **缓存预热**：

| 缓存类型 | 预热策略 | 实现 |
|---------|---------|------|
| 数据字典 | 应用启动全量加载 | ApplicationReadyEvent → dict type 全量预热 |
| 规则配置 | 变更主动失效 + 懒加载 | RuleLifecycleService 发布时 clear L1 |
| 租户配置 | L2 长 TTL + 本地监听 | Redis Keyspace Notification → 触发 L1 失效 |

2. **缓存穿透/击穿防护**：

```java
// 在 ydsz-common-cache 中封装 @CacheableWithProtection
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface CacheableWithProtection {
    String key();
    long ttl() default 300;
    boolean preventPenetration() default true;  // 空值缓存
    boolean preventBreakdown() default true;    // 互斥锁重建
}
```

3. **热点 Key 探测**：引入 Redis 4.0+ 的 `redis-cli --hotkeys` 或接入 Raptor（美团 TDP 热点探测 SDK）

### P2-4：数据库读写分离推进

**现状**：已引入 baomidou DynamicDataSource，但未见大量 `@DS` 注解使用，多数模块仍处于单数据源模式。

**建议推进路径**：

1. **识别读写分离候选表**（高频读低频写）：

| 引擎 | 候选表 | 读:写比估计 | 分离收益 |
|------|-------|-----------|---------|
| system | sys_dict_data / sys_config | > 50:1 | 高 |
| userinfo | sys_user（查询侧） | > 20:1 | 高 |
| message | msg_template | > 30:1 | 中 |
| workflow | flow_definition（已发布） | > 15:1 | 中 |

2. **最小侵入接入**：利用 baomidou `@DS("slave")` 注解标注查询方法，或通过 HintManager 强制走从库
3. **延迟敏感度分级**：对主从延迟敏感的查询（如刚写入后立即查询）强制走主库（HintManager.setMasterOnly()）

### P2-5：前端 Bundle 优化

**现状**：已引入 importmap 三级共享 + 按需引入 + lazy import + 图片压缩 + PWA，工程化水平良好。

**进一步优化**：

1. **Bundle 拆分策略审计**：检查各子应用的 Initial Bundle 体积，对 > 500KB 的子应用分析拆分点
2. **Preload/Prefetch**：对首屏高频访问的子应用启用 preload，对次屏低频的应用启用 prefetch
3. **Gzip/Brotli 预压缩**：在 Docker 构建阶段生成 `.br` / `.gz` 预压缩产物，Nginx 开启 `gzip_static on` / `brotli_static on`
4. **JSON 解析优化**：对大体积 JSON Schema（如工作流定义的 JSON Schema > 50KB）使用 `JSON.parse()` 而非对象字面量

## 六、体验改善维度

### P0-4：开发者体验（DX）提升

**现状**：开发者需同时理解后端自研编码规范 51 条、前端自研微内核、前后端统一契约生成体系，学习曲线陡峭。

**改进建议**：

1. **快速启动工具链**：

| 场景 | 工具 | 说明 |
|------|------|------|
| 后端新建 Module | 代码生成器 + 模板 fork | 基于 generator 模板创建新业务模块 |
| 前端新建 Page | `pnpm create-page` CLI | 从模板创建页面 + 路由注册 + API 调用脚手架 |
| 前后端联动开发 | `--live` 契约模式 | 后端启动后前端实时拉取 OpenAPI |
| 本地完整环境 | docker-compose 一键起 | MySQL + Redis + Nacos + MinIO + RocketMQ |

2. **规范即 Code**：将 51 条规范转化为 IDE 实时检测（IDEA Inspection Profile + ESLint 规则联动），开发者写代码时即获得反馈，而非 CI 阶段才报错

3. **脚手架文档**：编写《新人 30 分钟上手指南》，包含：本地环境搭建 → 创建第一个页面 → 联调接口 → 提交代码

## 结论

云顶微服务平台在架构设计、编码规范治理、自主技术研发（微内核、规则引擎、任务引擎）上已具备行业中等偏上水平，核心差异化能力（自研 ESM 微内核、三级 DDD 分层、统一编码规范 51 条）已在生产验证。

当前最主要的**阻断级瓶颈**是测试覆盖率几乎为零——这在 Spring Boot 4 + Spring Cloud 2025 这种前沿技术栈组合下，任何重构或升级都缺乏安全网。建议优先投入 15-25 人日实现核心引擎单测破零。

中长期看，**可观测性告警闭环**、**分布式事务按需落地**、**灰度发布全链路贯通**是进入生产级成熟度的三块敲门砖；**Agent 引擎生产就绪度**是差异化竞争力能否兑现的关键变量。
