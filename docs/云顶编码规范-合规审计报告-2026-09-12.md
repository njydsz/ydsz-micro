## 六、规范自身缺陷（核心发现：应改规范，而非改代码）

审计中最有价值的判断是：**部分"违规"源于规范与工程现实的冲突，机械整改将造成负收益。**

### 6.1　§2.1 / §4.4 组件文件命名：规范与工程系统性冲突

规范要求「Vue 组件文件名 PascalCase」，但实测：

| 目录 | kebab-case | PascalCase |
| ---- | ---------- | ---------- |
| 全仓 `.vue`（599） | **438（73%）** | 161（27%） |
| `views/` | **201** | 22 |
| `components/` | **70** | 1 |
| `comm/@core/ui-kit/shadcn-ui/src/ui/**`（生成件） | 少 | **绝大多数** |

真相是：**工程沿用了 Vue 生态主流约定（页面与业务组件 kebab-case），PascalCase 仅存在于 shadcn-ui 生成件**。规范 §4.4 的示例恰好引用了 `shadcn-ui/.../Button.vue`，却把该生成件约定推广为全仓强制条款，导致 check-standard 报出 **307 项"僵尸违规"**。

**建议**：修订 §2.1/§4.4，按目录分层定义——
- 基础 UI 组件 / 生成件（`comm/@core/ui-kit/**`）：PascalCase
- 页面级视图（`views/`）与业务组件（`components/`）：kebab-case（与 ESLint `vue/component-name-in-template-casing` 配合落地）

### 6.2　规范自引用的审计工具自身不合规（§15.8）

§15.8 将 `.workbuddy/tmp/audit-comments.mjs` 列为「注释覆盖率度量」门禁，但该文件：
- 被 ESLint 扫描（`.workbuddy/**` 未加入 ignore）→ 贡献 8 个 lint 错误
- 且 `.workbuddy/**` **已被 git 跟踪**（含 `verify-contract/*.py` 等 5 个脚本）

**建议**：二选一 —— 要么把 `.workbuddy/tmp` 加入 ESLint `ignores`（临时脚本目录本就不该 lint），要么将审计脚本正式化迁入 `bash/` 并纳入 lint 范围。

### 6.3　§12.2 代码示例已过时

规范 §12.2 示例：

```typescript
import { defineSubApp } from '@ydsz/micro-runtime';
export default defineSubApp({ bootstrap, mount, unmount });
```

实际工程（`apps/system-web/src/main.ts` 等 9 个子应用一致）：


且 `comm/effects/micro-runtime/src/define-sub-app.ts:16` 已明确标注 `@deprecated —— 统一迁移至 @ydsz/shared-auth 的 createSubApp`。**规范在教人用已废弃 API，必须更新。**
