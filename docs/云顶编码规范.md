## 1. 总则

### 1.1 规范级别定义

| 级别     | 说明                         | 标识 |
| -------- | ---------------------------- | ---- |
| 【强制】 | 必须遵守，违反将导致 PR 拒绝 | 🔴   |
| 【推荐】 | 建议遵守，需充分理由方可偏离 | 🟡   |
| 【参考】 | 最佳实践建议，可灵活采纳     | 🟢   |

### 1.2 核心原则

1. **一致性**：同一项目内保持代码风格一致
2. **可读性**：代码是写给人看的，其次才是机器执行
3. **可维护性**：模块职责清晰，依赖关系明确
4. **类型安全**：充分利用 TypeScript 类型系统，减少运行时错误
5. **复用性**：公共能力下沉到 comm 模块，避免重复实现

## 2. 命名规范

### 2.1 文件命名

> **【强制】** 文件命名遵循以下规则：

| 文件类型    | 命名规则                             | 示例                               |
| ----------- | ------------------------------------ | ---------------------------------- |
| Vue 组件    | PascalCase                           | `UserProfile.vue`、`AppHeader.vue` |
| composables | use + 功能名（camelCase）            | `useAuth.ts`、`usePagination.ts`   |
| store 模块  | 功能名（camelCase）                  | `auth.ts`、`notification.ts`       |
| 工具函数    | camelCase                            | `dateUtils.ts`、`formatHelper.ts`  |
| 类型文件    | 功能名 + `.d.ts` 或 `types.ts`       | `user.d.ts`、`api-types.ts`        |
| 常量文件    | camelCase 或 SCREAMING_SNAKE_CASE    | `core.ts`、`API_ENDPOINTS.ts`      |
| 样式文件    | 与组件同名                           | `UserProfile.scss`                 |
| 测试文件    | 被测文件名 + `.test.ts` / `.spec.ts` | `auth.test.ts`、`useAuth.spec.ts`  |

### 2.2 目录命名

> **【强制】** 目录命名遵循以下规则：

| 场景     | 规则       | 示例                                    |
| -------- | ---------- | --------------------------------------- |
| 普通目录 | kebab-case | `user-info/`、`common-ui/`              |
| 复数资源 | 复数形式   | `components/`、`composables/`、`views/` |
| 缩写目录 | 全小写     | `api/`、`utils/`、`hooks/`              |

### 2.3 变量与函数命名

> **【强制】** 变量和函数使用 camelCase 命名，必须见名知意。

```typescript
// ✅ 正确
const userName = 'John';
const isLoading = false;
function fetchUserData() {}
function handleSubmit() {}

// ❌ 错误
const u = 'John';
const flag = false;
function getData() {}
function click() {}
```

### 2.4 常量命名

> **【强制】** 常量使用 SCREAMING_SNAKE_CASE 命名。

```typescript
// ✅ 正确
const MAX_RETRY_COUNT = 3;
const DEFAULT_PAGE_SIZE = 20;
const API_BASE_URL = '/api/v1';

// ❌ 错误
const maxRetryCount = 3;
const defaultPageSize = 20;
```

### 2.5 类型与接口命名

> **【推荐】** 类型使用 PascalCase 命名，接口可加 `I` 前缀或不加（项目内统一）。

```typescript
// ✅ 正确（本项目风格：接口不加 I 前缀）
interface UserInfo {
  id: number;
  name: string;
  email: string;
}

interface BaseResponse<T = unknown> {
  code: string;
  msg: string;
  data: T;
}

// 类型别名同样 PascalCase
type RequestConfig = {
  baseURL?: string;
  timeout?: number;
};
```

### 2.6 CSS 类名命名

> **【强制】** CSS 类名使用 BEM 命名规范或 Tailwind CSS 原子类。

```scss
// BEM 命名（自定义样式场景）
.user-card {
  // Block
  &__header {
    // Element
    padding: 16px;
  }
  &--active {
    // Modifier
    border-color: #1890ff;
  }
}
```

## 3. TypeScript 规范

### 3.1 类型声明

> **【强制】** 禁止使用 `any`
> 类型，必须显式声明类型。特殊情况需添加注释说明理由。

```typescript
// ✅ 正确
function getUser(id: number): Promise<UserInfo> {
  return request.get(`/users/${id}`);
}

// ❌ 错误
function getUser(id: any): any {
  return request.get(`/users/${id}`);
}

// ⚠️ 特殊场景（需注释说明）
function parseResponse(resp: unknown): UserInfo {
  // 外部数据来源不可控，需运行时校验
  return resp as UserInfo;
}
```

> **【强制·豁免条款】** 第三方生成组件库（如
> `comm/@core/ui-kit/shadcn-ui`）由 CLI 生成，其受控 `any`
> 透传不可控，已在 ESLint 执行层对该目录豁免
> `@typescript-eslint/no-explicit-any`。**业务代码（apps/\*、comm/effects/\*、main/\* 非生成件）严禁任何
> `any`**，违反须消除或加 `// 非标准 API 收窄` 类注释说明。

### 3.2 接口与类型别名选择

> **【推荐】** 优先使用 `interface` 定义对象类型，`type`
> 用于联合类型、交叉类型、函数类型等场景。

```typescript
// ✅ 对象类型用 interface
interface UserInfo {
  id: number;
  name: string;
}

// ✅ 联合类型用 type
type Status = 'pending' | 'success' | 'error';

// ✅ 函数类型用 type
type RequestHandler = (config: RequestConfig) => RequestConfig;
```

### 3.3 泛型使用

> **【推荐】** 通用工具函数和组件应使用泛型提升复用性。

```typescript
// ✅ 泛型函数
function filterList<T>(list: T[], predicate: (item: T) => boolean): T[] {
  return list.filter(predicate);
}

// 泛型响应类型
interface ApiResponse<T = unknown> {
  code: string;
  data: T;
  message: string;
}
```

### 3.4 严格模式

> **【强制】**
> 项目启用 TypeScript 严格模式（`strict: true`），禁止关闭以下选项：

```json
{
  "compilerOptions": {
    "strict": true,
    "noImplicitAny": true,
    "strictNullChecks": true,
    "strictFunctionTypes": true,
    "strictBindCallApply": true,
    "noImplicitThis": true,
    "alwaysStrict": true
  }
}
```

### 3.5 模块导入导出

> **【强制】** 导入导出遵循以下规则：

```typescript
// ✅ 正确：类型导入使用 type 关键字
import type { UserInfo } from '@ydsz/types';
import { ref, computed } from 'vue';

// ✅ 正确：路径别名使用项目配置的别名
import { useAuthStore } from '#/store/auth';
import { requestClient } from '#/api/request';

// ❌ 错误：混用类型和值导入（未区分 type）
import { UserInfo, useAuthStore } from './types';
```

### 3.6 可选链与空值合并

> **【推荐】** 优先使用可选链 `?.` 和空值合并 `??` 处理空值。

```typescript
// ✅ 正确
const userName = user?.profile?.name ?? 'Unknown';
const total = data?.list?.length ?? 0;

// ❌ 错误：冗长的空值判断
const userName =
  user && user.profile && user.profile.name ? user.profile.name : 'Unknown';
```

## 4. Vue 组件规范

### 4.1 组件结构

> **【强制】** Vue 单文件组件遵循 `<script setup>`
> 优先原则，结构顺序为：`<script setup>` → `<template>` → `<style>`。

```vue
<script setup lang="ts">
// 1. 导入语句
import { ref, computed, onMounted } from 'vue';
import type { PropType } from 'vue';

// 2. 类型定义
interface UserInfo {
  id: number;
  name: string;
}

// 3. Props 定义
const props = defineProps({
  user: {
    type: Object as PropType<UserInfo>,
    required: true,
  },
});

// 4. Emits 定义
const emit = defineEmits<{
  (e: 'update', value: string): void;
  (e: 'delete', id: number): void;
}>();

// 5. 响应式数据
const isLoading = ref(false);
const searchText = ref('');

// 6. 计算属性
const displayName = computed(() => props.user.name || 'Unknown');

// 7. 方法
function handleClick() {
  emit('update', searchText.value);
}

// 8. 生命周期
onMounted(() => {
  // 初始化逻辑
});
</script>

<template>
  <div class="user-card">
    <h3>{{ displayName }}</h3>
    <button @click="handleClick">更新</button>
  </div>
</template>

<style scoped lang="scss">
.user-card {
  padding: 16px;
}
</style>
```

### 4.2 Props 定义

> **【强制】**
> Props 必须使用 TypeScript 类型声明，禁止使用简单的数组或对象形式。

```typescript
// ✅ 正确：使用泛型定义
interface Props {
  title: string;
  count?: number;
  status?: 'active' | 'inactive';
}

const props = withDefaults(defineProps<Props>(), {
  count: 0,
  status: 'active',
});

// ❌ 错误：简单对象形式
const props = defineProps({
  title: String,
  count: Number,
});
```

### 4.3 事件命名

> **【强制】** 事件名称使用 camelCase，模板中使用 kebab-case。

```typescript
// ✅ 正确
const emit = defineEmits<{
  (e: 'item-click', item: Item): void;
  (e: 'status-change', status: string): void;
}>();

// 模板中使用
<MyComponent @item-click="handleClick" @status-change="handleStatusChange" />
```

### 4.4 组件命名

> **【强制】** 组件文件名和组件名使用 PascalCase。

```vue
<!-- ✅ 正确 -->
<!-- 文件：UserProfile.vue -->
<script setup lang="ts">
defineOptions({ name: 'UserProfile' });
</script>

<!-- ❌ 错误 -->
<!-- 文件：user-profile.vue -->
<script setup lang="ts">
defineOptions({ name: 'userProfile' });
</script>
```

### 4.5 组件职责

> **【推荐】** 单一职责原则：一个组件只负责一个功能，超过 300 行应考虑拆分。

| 组件类型               | 职责                     | 示例                              |
| ---------------------- | ------------------------ | --------------------------------- |
| 视图组件（views）      | 页面级组件，负责页面布局 | `DashboardView.vue`               |
| 业务组件（components） | 可复用的业务逻辑组件     | `UserSelector.vue`                |
| 基础组件（ui-kit）     | 纯 UI 组件，无业务逻辑   | `BaseButton.vue`、`BaseInput.vue` |

### 4.6 v-for 与 key

> **【强制】** `v-for` 必须绑定 `:key`，禁止使用索引作为 key。

```vue
<!-- ✅ 正确 -->
<UserCard v-for="user in userList" :key="user.id" :user="user" />

<!-- ❌ 错误 -->
<UserCard v-for="(user, index) in userList" :key="index" :user="user" />
```

### 4.7 条件渲染

> **【推荐】** 使用 `v-if` / `v-else-if` / `v-else` 进行条件渲染，避免 `v-show`
> 滥用。

```vue
<!-- ✅ 正确：频繁切换用 v-show -->
<div v-show="isVisible">频繁显示/隐藏的内容</div>

<!-- ✅ 正确：条件渲染用 v-if -->
<LoadingSpinner v-if="isLoading" />
<ErrorState v-else-if="hasError" />
<UserList v-else :users="users" />
```

### 4.8 插槽使用

> **【推荐】** 具名插槽使用模板语法，作用域插槽使用解构。

```vue
<!-- ✅ 正确 -->
<template #header>
  <h2>标题</h2>
</template>

<template #default="{ item, index }">
  <span>{{ index }}: {{ item.name }}</span>
</template>
```

## 5. 性能规范

### 5.1 组件懒加载

> **【强制】** 路由组件必须使用动态导入懒加载，减少首屏加载体积。

```typescript
// ✅ 正确：路由组件懒加载
const routes: RouteRecordRaw[] = [
  {
    path: '/dashboard',
    component: () => import('#/views/dashboard/index.vue'),
  },
  {
    path: '/user',
    component: () => import('#/views/user/index.vue'),
  },
];

// ✅ 正确：大型组件按需加载
const HeavyChart = defineAsyncComponent(() => import('./HeavyChart.vue'));

// ❌ 错误：静态导入大组件
import HeavyChart from './HeavyChart.vue';
```

### 5.2 列表虚拟化

> **【强制】** 超过 50 条数据的列表必须使用虚拟滚动，避免渲染大量 DOM 节点。

```vue
<!-- ✅ 正确：使用虚拟滚动 -->
<RecycleScroller
  class="scroller"
  :items="largeList"
  :item-size="64"
  key-field="id"
  v-slot="{ item }"
>
  <ListItem :item="item" />
</RecycleScroller>

<!-- ✅ 正确：使用 vxe-table 虚拟滚动 -->
<vxe-table :data="largeList" :scroll-y="{ enabled: true, gt: 50 }">
  <vxe-column field="name" title="名称" />
</vxe-table>

<!-- ❌ 错误：直接渲染大量数据 -->
<div v-for="item in largeList" :key="item.id">
  <ListItem :item="item" />
</div>
```

### 5.3 图片优化

> **【推荐】** 图片资源遵循以下优化策略：

| 场景       | 规范                                       |
| ---------- | ------------------------------------------ |
| 格式选择   | 优先使用 WebP 格式，兼容性兜底使用 PNG/JPG |
| 懒加载     | 首屏外图片必须使用 `loading="lazy"`        |
| 尺寸指定   | 必须指定 width/height 避免布局偏移（CLS）  |
| 响应式图片 | 使用 `srcset` 提供不同分辨率图片           |
| 大图处理   | 超过 200KB 的图片必须压缩                  |

```vue
<!-- ✅ 正确：图片懒加载 + 尺寸指定 -->
<img
  src="hero.webp"
  srcset="hero-400.webp 400w, hero-800.webp 800w, hero-1200.webp 1200w"
  sizes="(max-width: 768px) 100vw, 50vw"
  width="800"
  height="400"
  loading="lazy"
  alt="首页横幅"
/>
```

### 5.4 防抖与节流

> **【强制】** 高频触发事件必须使用防抖或节流控制执行频率。

```typescript
import { useDebounceFn, useThrottleFn } from '@vueuse/core';

// ✅ 搜索输入使用防抖（300ms）
const handleSearch = useDebounceFn((keyword: string) => {
  searchApi.query(keyword);
}, 300);

// ✅ 滚动事件使用节流（100ms）
const handleScroll = useThrottleFn(() => {
  updateScrollPosition();
}, 100);

// ✅ 窗口 resize 使用防抖
const handleResize = useDebounceFn(() => {
  recalculateLayout();
}, 200);
```

| 场景        | 策略 | 延迟            |
| ----------- | ---- | --------------- |
| 搜索输入    | 防抖 | 300ms           |
| 滚动事件    | 节流 | 100ms           |
| 窗口 resize | 防抖 | 200ms           |
| 按钮点击    | 节流 | 500ms           |
| 拖拽事件    | 节流 | 16ms（约60fps） |

### 5.5 内存管理

> **【强制】** 组件卸载时必须清理资源，防止内存泄漏。

```typescript
// ✅ 正确：完整资源清理
onMounted(() => {
  // 定时器
  timerId = setInterval(fetchData, 5000);

  // 事件监听
  window.addEventListener('resize', handleResize);

  // 请求控制器
  abortController = new AbortController();
  fetchData({ signal: abortController.signal });

  // WebSocket 连接
  wsConnection = new WebSocket(url);
});

onUnmounted(() => {
  // 清理定时器
  clearInterval(timerId);

  // 移除事件监听
  window.removeEventListener('resize', handleResize);

  // 取消请求
  abortController?.abort();

  // 关闭连接
  wsConnection?.close();
});
```

### 5.6 计算缓存

> **【推荐】** 复杂计算使用 `computed` 缓存，避免模板中直接调用函数。

```vue
<!-- ✅ 正确：使用计算属性 -->
<script setup lang="ts">
const expensiveResult = computed(() => {
  return heavyComputation(data.value);
});
</script>
<template>
  <div>{{ expensiveResult }}</div>
</template>

<!-- ❌ 错误：模板中直接调用函数（每次渲染都执行） -->
<template>
  <div>{{ heavyComputation(data) }}</div>
</template>
```

### 5.7 组件缓存

> **【推荐】** 频繁切换的组件使用 `<KeepAlive>` 缓存状态。

```vue
<!-- ✅ 正确：缓存频繁切换的组件 -->
<router-view v-slot="{ Component }">
  <KeepAlive :include="['UserList', 'DashboardView']">
    <component :is="Component" />
  </KeepAlive>
</router-view>
```

## 6. API 请求规范

### 6.1 请求客户端使用

> **【强制】** 统一使用 `@ydsz/request` 提供的请求客户端，禁止直接使用 `axios`
> 或 `fetch`。

```typescript
// ✅ 正确：使用共享请求客户端
import { requestClient, baseRequestClient } from '#/api/request';

// 带鉴权的请求
const userData = await requestClient.get<UserInfo>('/api/user/profile');

// 公共接口请求（登录、刷新令牌等）
const loginResp = await baseRequestClient.post<LoginResponse>(
  '/api/auth/login',
  loginForm,
);
```

> **【强制·例外条款】** 以下**基础设施层**场景允许直接使用
> `fetch`/`axios`（无统一请求客户端上下文）：Service
> Worker 网络代理、微内核健康检查/版本清单/资源清单加载、监控上报（`@ydsz/monitor`）。**此类直用必须在函数上方加
> `// @infra-fetch 基础设施层直用，无统一客户端上下文`
> 注释**，业务层（apps/\*、comm/effects/\* 非基础设施、main/\* 非 SW）仍一律禁止。

### 6.2 API 模块组织

> **【强制】** API 接口按业务模块组织，每个模块一个文件。

```
api/
├── index.ts          # 导出入口
├── request.ts        # 请求客户端配置
└── core/
    ├── index.ts      # 模块导出
    ├── auth.ts       # 认证相关接口
    ├── user.ts       # 用户相关接口
    └── dashboard.ts  # 仪表盘相关接口
```

### 6.3 接口定义规范

> **【强制】** API 函数必须定义参数类型和返回类型，使用项目统一的
> `BaseResponse<T>` 类型。

```typescript
// ✅ 正确
import type { BaseResponse, PageResponse, PageQuery } from '@ydsz/types';

/** 获取用户信息 */
export function getUserInfo(): Promise<BaseResponse<UserInfo>> {
  return requestClient.get('/api/user/info');
}

/** 分页查询用户列表 */
export function queryUserList(
  params: PageQuery & { keyword?: string },
): Promise<PageResponse<UserInfo>> {
  return requestClient.get('/api/user/list', { params });
}

/** 创建用户 */
export function createUser(data: CreateUserDto): Promise<BaseResponse<number>> {
  return requestClient.post('/api/user', data);
}
```

## 8. 状态管理规范

### 8.1 Store 类型

> **【强制】** 使用 Pinia 的 Composition API 风格（`setup`
> 语法），禁止使用 Options API 风格。

```typescript
// ✅ 正确：setup 语法
export const useAuthStore = defineStore('auth', () => {
  // 状态
  const userInfo = ref<UserInfo | null>(null);
  const token = ref<string | null>(null);

  // 计算属性
  const isLoggedIn = computed(() => !!token.value);

  // 方法
  function setToken(newToken: string | null) {
    token.value = newToken;
  }

  async function login(credentials: LoginDto) {
    const resp = await loginApi(credentials);
    token.value = resp.data.token;
    userInfo.value = resp.data.userInfo;
  }

  function logout() {
    token.value = null;
    userInfo.value = null;
  }

  return { userInfo, token, isLoggedIn, setToken, login, logout };
});
```

## 15. 代码度量规范

### 15.1 文件行数

> **【强制】**
> 逻辑代码单文件行数不超过下表上限，超过应考虑拆分。类型声明与资源类文件按豁免条款执行。

| 文件类型                                | 最大行数 | 级别     | 说明                                                        |
| --------------------------------------- | -------- | -------- | ----------------------------------------------------------- |
| Vue SFC（单文件组件）                   | 1000 行  | 【强制】 | 含 `<template>` + `<script>` + `<style>` 合计               |
| 业务逻辑文件（composables/store/utils） | 500 行   | 【强制】 | 含函数体与控制流的逻辑代码                                  |
| 纯配置/数据文件                         | 1000 行  | 【强制】 | 需在文件顶部注释说明 `// @data-file 纯数据定义，无业务逻辑` |
| 测试文件                                | 500 行   | 【参考】 | 超长时按模块拆分为 `*.test.ts`                              |
| 类型声明文件（types.ts / *.d.ts）       | 1500 行  | 【参考】 | 超出后按模块拆分为多个 `*-types.ts`                         |

**豁免条款（2026-08-24 修订）**：

> **背景**：行数限制应服务于代码质量，而非机械指标。Vue
> SFC 因包含 template/script/style 三块结构，1000 行已能承载复杂组件；纯配置/数据文件无业务逻辑，1000 行上限可接受，但需注释说明以便工具识别。

| 豁免类别          | 判定标准                                                                 | 要求                                                                                                             |
| ----------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| 类型声明文件      | 文件以 `type` / `interface` 声明为主，不含函数体与控制流（if/for/while） | 单独按 1500 行设限；超出后按模块拆分为多个 `*-types.ts`                                                          |
| SVG / 图标资源    | 纯内联 SVG 的 `.vue` 组件（template 内仅 `<svg>`）                       | 豁免行数限制；但超过 2000 行必须抽离为独立 `.svg` 静态资源，通过 `vite-plugin-font` 或静态引用加载，禁止继续内联 |
| 常量 / 配置数据   | 纯数据定义（枚举、配置表、语言包），无函数体                             | 按 1000 行设限；需在文件顶部添加 `// @data-file` 注释说明；数据超过 500 项拆分到独立文件按模块组织               |
| 语言包（locales） | JSON 翻译文件                                                            | 豁免；按模块拆分 `zh-CN/*.json` / `en-US/*.json`                                                                 |

> **判定工具**：文件不含 `function` / `const xx = () =>` / `if (` / `for (`
> 等控制流与函数体语法，即视为声明/资源类文件，适用豁免条款。纯配置/数据文件需保留
> `// @data-file` 注释以便自动化工具识别。

### 15.2 文件拆分规范

> **【强制】**
> 文件的拆分与合并必须服务于代码质量，**禁止为了规避行数指标而恶意拆分大文件**。规范是质量的助手，不是对立的度量游戏。

#### 15.2.1 核心理念

**"规范服务于代码质量，而非代码质量服务于规范"**：

- 拆分的唯一正当理由是**提升代码的可读性、可维护性或复用性**
- 行数上限是**预警信号**，不是"必须拆分"的指令
- 一个内聚、清晰的大文件，远胜于一个被拆成多个碎片的"指标达标"文件

#### 15.2.2 恶意拆分判定（禁止行为）

> **【强制】** 出现以下任一情形，视为恶意拆分，PR 必须打回：

| 判定特征                     | 说明                                                              | 示例                                                                              |
| ---------------------------- | ----------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| **无内聚主题的机械切割**     | 将一个完整业务逻辑/组件按行数点物理切断，拆出的文件之间无明确边界 | 把一个 600 行的表单组件从第 300 行砍成两个文件，但数据流和逻辑仍高度耦合          |
| **拆出无独立意义的碎片文件** | 拆分后的子文件无法独立命名、无法脱离上下文理解                    | 拆成 `part1.ts` / `part2.ts`、`temp-a.vue` / `temp-b.vue`，文件名反映不出独立职责 |
| **导入关系呈网状交叉**       | 拆分后的文件互相 import，形成循环依赖或过度耦合                   | A 引用 B、B 引用 A，或 A/B/C 三方交叉引用                                         |
| **单文件行数过低**           | 拆分后出现大量 10-30 行的"孤儿文件"，未与同模块归并               | 一个目录下有 15 个 20 行左右的文件，原本是一个完整模块                            |
| **仅修改未拆分**             | 为规避检查，把未修改的代码原封不动搬到新文件                      | 新增一个 `utils-extra.ts`，内容是从原文件复制的 5 个未改动函数                    |

```typescript
// ❌ 恶意拆分示例：把内聚的 UserForm 组件强行拆成两个文件
// 文件1：UserFormPart1.vue（320行）
const formData = ref({ name: '', email: '' });
const errors = ref<Record<string, string>>({});
function validate() {
  /* ... */
}
// 302 行模板和逻辑...

// 文件2：UserFormPart2.vue（290行）

  /* ... */
}; // 依赖 formData、errors、validate
// 拆出后两个文件必须同时导入才能运行，毫无独立价值

// ✅ 正确做法：保持 UserForm.vue 完整（610 行，但职责内聚、逻辑清晰）
// 在 15.1 行数超限预警时，优先提取可复用的校验逻辑到 useFormValidation.ts，
// 而不是把组件从中间劈开
```

#### 15.2.3 合理拆分的判定标准

> **【推荐】** 满足以下**至少一条**，方可考虑拆分：

| 拆分动机          | 判定条件                                                                    | 推荐做法                                       |
| ----------------- | --------------------------------------------------------------------------- | ---------------------------------------------- |
| **可复用性**      | 某段代码在其他模块被使用 2 次以上，或有明确复用预期                         | 抽取为独立工具函数 / composable / 子组件       |
| **独立职责**      | 文件包含泾渭分明的两个职责（如"数据获取 + 复杂 UI 渲染"），且各自可独立测试 | 拆分为容器组件 + 展示组件，或 hook + 组件      |
| **复杂度隔离**    | 某段逻辑本身复杂度较高（如复杂算法、复杂表单联动），混在主文件中降低可读性  | 提取为独立模块，主文件保留编排逻辑             |
| **类型/资源聚合** | 类型声明纯粹因为聚合了多个领域的类型而超长                                  | 按领域拆分为 `user-types.ts`、`order-types.ts` |

**拆分前的自检清单**：

1. 拆出的部分能否用**一个独立的业务名词**命名？（能 → 可拆；不能 → 继续内聚）
2. 拆出后，**原文件的使用者是否需要同时导入多个拆分文件才能工作**？（是 → 拆分方案错误）
3. 拆分后，**每个文件是否还能保持合理的行数**？（拆出 10-30 行的碎片 → 应归并到同模块）
4. 这段代码**是否会被其他地方复用或独立修改**？（否 → 拆出的价值存疑）

#### 15.2.4 拆分后的文件组织

> **【强制】** 拆分后的文件必须遵循以下组织规范：

| 文件数量   | 组织要求                                             |

| 4+ 个文件  | 必须归并到**独立子目录**，子目录以主模块命名         |

```typescript
  USER_ALREADY_EXISTS = '20002',
  USER_PASSWORD_ERROR = '20003',
  USER_DISABLED = '20004',

  // 订单模块错误 3xxxx
  ORDER_NOT_FOUND = '30001',
  ORDER_EXPIRED = '30002',
  ORDER_STATUS_ERROR = '30003',

  // 支付模块错误 4xxxx
  PAYMENT_FAILED = '40001',
  PAYMENT_TIMEOUT = '40002',
  REFUND_FAILED = '40003',
}

// 业务错误类
class BusinessError extends Error {
  constructor(
    public code: ErrorCode,
    message: string,
    public details?: Record<string, unknown>,
  ) {
    super(message);
    this.name = 'BusinessError';
  }
}

// 使用示例
function handleResponse(response: ApiResponse) {
  if (response.code !== ErrorCode.SUCCESS) {
    throw new BusinessError(response.code, response.msg, {
      originalResponse: response,
    });
  }
  return response.data;
}
```

### 17.8 Git 分支规范

> **【强制】** 分支命名和管理遵循以下规则：

```
分支命名规范：
- 功能分支：feature/<功能描述>        例：feature/user-export
- 修复分支：fix/<问题描述>            例：fix/login-redirect
- 热修复分支：hotfix/<问题描述>        例：hotfix/payment-error
- 发布分支：release/<版本号>           例：release/v1.2.0
- 开发分支：develop                    例：develop
- 主分支：main                         例：main
```

| 规则     | 说明                                     |
| -------- | ---------------------------------------- |
| 保护分支 | main 和 develop 为保护分支，禁止直接推送 |
| 分支命名 | 使用 kebab-case，描述清晰                |
| PR 要求  | 必须至少 1 人 Review 通过                |
| 合并策略 | 使用 Squash Merge 保持主分支整洁         |
| 分支清理 | 合并后删除源分支                         |

## 18. 代码审查清单

### 18.1 Pre-PR 自查清单

提交 PR 前，开发者应逐项确认：

#### 基础规范

- [ ] 代码通过 ESLint 检查（`pnpm lint`）
- [ ] 代码通过 TypeScript 类型检查（`pnpm type-check`）
- [ ] 样式检查通过（`pnpm stylelint`）
- [ ] 提交信息符合 Conventional Commits 规范

#### 类型与命名

- [ ] 无 `any` 类型（特殊情况已注释说明）
- [ ] 变量和函数命名符合 camelCase 规范
- [ ] 常量使用 SCREAMING_SNAKE_CASE 命名
- [ ] Props 和 Emits 使用 TypeScript 类型声明

#### Vue 组件

- [ ] 组件使用 `<script setup>` 语法
- [ ] 组件文件名使用 PascalCase
- [ ] Vue SFC 不超过 1000 行（含 template/script/style）
- [ ] 业务逻辑文件（composables/store/utils）不超过 500 行
- [ ] 纯配置/数据文件不超过 1000 行（需添加 `// @data-file` 注释说明）
- [ ] `v-for` 使用唯一 `:key`，禁止索引作为 key

#### API 与状态

- [ ] API 请求使用统一的请求客户端
- [ ] API 函数定义参数类型和返回类型
- [ ] 错误处理完善，无静默失败
- [ ] Pinia Store 使用 setup 语法

#### 性能

- [ ] 路由组件使用懒加载
- [ ] 超过 50 条数据的列表使用虚拟滚动
- [ ] 图片使用懒加载（首屏外）
- [ ] 高频事件使用防抖/节流
- [ ] `onUnmounted` 清理定时器、事件监听

#### 安全

- [ ] 用户输入已转义，禁止直接使用 `v-html`
- [ ] 无硬编码密钥或敏感信息
- [ ] 日志输出已脱敏

#### 样式与可访问性

- [ ] 样式使用 Tailwind 优先
- [ ] 组件样式使用 scoped 或 CSS Modules
- [ ] 使用语义化 HTML 标签
- [ ] 交互元素支持键盘操作
- [ ] 图标按钮提供 aria-label

#### 质量

- [ ] 无重复代码，公共能力已下沉到 comm 模块

#### 文件拆分

- [ ] 拆分动机是提升可维护性/复用性，而非规避行数指标
- [ ] 拆分后的文件有独立、可理解的命名（非 part1/temp-a 等无意义名称）
- [ ] 拆分后的文件未形成循环依赖或交叉 import
- [ ] 拆分后的碎片文件（<30 行）已归并到同模块，而非散落目录

#### 日志与监控

- [ ] 关键操作有日志记录
- [ ] 生产环境无 console.log
- [ ] 错误已上报监控系统

### 18.2 审查关注点

| 关注点   | 说明                                                     |
| -------- | -------------------------------------------------------- |
| 类型安全 | 检查是否有 `any` 滥用、类型断言是否合理                  |
| 组件设计 | 职责是否单一、是否可复用、Props 是否过多                 |
| 性能     | 是否有不必要的重复渲染、大数据是否使用虚拟滚动           |
| 安全     | XSS 防护、敏感信息是否暴露、URL 协议校验                 |
| 可访问性 | 键盘导航、屏幕阅读器支持、ARIA 属性                      |
| 代码度量 | 文件行数、函数复杂度、嵌套深度                           |
| 文件拆分 | 拆分动机是否正当、碎片文件是否归并、依赖方向是否树状向下 |

### 18.3 性能审查要点

- [ ] 首屏加载时间是否可优化
- [ ] 大数据列表是否使用虚拟滚动
- [ ] 图片是否压缩和懒加载
- [ ] 是否存在内存泄漏（定时器、事件监听）
- [ ] 计算属性是否合理使用缓存

### 18.4 安全审查要点

- [ ] XSS：用户输入是否转义
- [ ] CSRF：状态变更请求是否有 Token
- [ ] 敏感信息：日志、错误信息是否脱敏
- [ ] 依赖安全：是否有已知漏洞
