# ydsz-micro × ydsz-cloud 接口适配差距分析与优化建议

> **审计日期**：2026-08-24
> **审计对象**：前端 `D:\Code\open\ydsz-micro`（8 个微应用 + comm 公共层）× 后端 `D:\Code\open\ydsz-cloud`（9 服务 152 Controller）
> **审计方法**：静态扫描后端全部 `*Controller.java` 的类级 + 方法级映射注解（932 个端点），提取前端全部 `requestClient` 调用（296 个，含 `comm/effects/shared-auth`），做路径归一化（路径变量 `${id}` ↔ `{id}`、camelCase ↔ kebab-case、literule 路径别名）与 HTTP 动词精确匹配。**以代码事实为准，不臆测。**

## 二、P0：先修链路，再铺功能（不修则一切适配无效）

### P0-1 literule 前后端路径体系断裂（整服务 404）

- **前端**调用 `/api/v1/literule/**`（如 `apps/literule-web/src/api/rule.ts` 的 `/api/v1/literule/rules/page`）。
- **后端** Controller 全部挂载在 `/v1/rule-engine/**`（`RuleAdminController` → `/v1/rule-engine/rules` 等 24 个 Controller）。
- **网关** `routes-nacos.yaml` 路由 `/api/v1/literule/**` → `lb://ydsz-literule`，**无 RewritePath / StripPrefix 过滤器**，原样转发 → 后端无 `/api/v1/literule/**` Controller → **全量 404**。
- 同时 literule-web 的 30 个调用几乎全部是虚构路径（`/rules/page`、`/rules/list`、`PUT /rules`、`DELETE /rules/{id}` 在后端均不存在），后端真实端点语义完全不同（`GET /v1/rule-engine/rules`、`/{ruleCode}/versions`、`/dry-run` 等）。

**修复方向（二选一，推荐 A）**：
- **A（后端改）**：ydsz-cloud 将 literule 全部 Controller 基础路径统一为 `/api/v1/literule/**`，与其余 7 个服务对齐；并在 ArchUnit 增加规则：Controller 类级映射必须以 `/api/v1/{serviceName}/` 开头。
- **B（网关改）**：为 literule 路由增加 `RewritePath=/api/v1/literule/(?<segment>.*), /v1/rule-engine/$`。仅作过渡，不解决规范分裂。

### P0-2 userinfo 五个 Controller 路径使用实体类名（后端 bug）

代码事实：

| Controller | 类级 @RequestMapping（现状） | 前端调用 | 结果 |
|------------|------------------------------|----------|------|
| RoleController | `/api/v1/RoleDO` | `/api/v1/role/**` | 404 |
| MenuController | `/api/v1/MenuDO` | `/api/v1/menu/**` | 404 |
| CompanyController | `/api/v1/CompanyDO` | `/api/v1/company/**` | 404 |
| LanguageController | `/api/v1/LanguageDO` | `/api/v1/language/**` | 404 |
| PostController | `/api/v1/PostDO` | `/api/v1/post/**` | 404 |

**修复**：后端改为小写资源名（`/api/v1/role` 等），并补 ArchUnit 规则：路径段禁止匹配 `[A-Z]` 与 `DO/VO/DTO$` 后缀。

### P0-3 命名风格漂移：camelCase vs kebab-case（运行时 404）

| 前端（message-web） | 后端实际 | 
|--------------------|----------|
| `GET /api/v1/message/deadLetter/page` | `/api/v1/message/dead-letter/**` |
| `GET/POST/DELETE /api/v1/message/routeRule/**`（4 处） | `/api/v1/message/route-rule/**` |

**修复**：前端统一改 kebab-case；同时在 gen:api 契约门禁（见 P0-4）落地后由 CI 兜底。

### P0-4 OpenAPI 契约工具链"纸面化"——漂移无人发现的根因

- `bash/gen-api.mjs` 已实现（含 `--check` CI 模式与 `.api-contract.lock` 哈希锁），`package.json` 已注册 `gen:api` / `gen:api:check`。
- **但**：8 个 `apps/*/src/api/sdk` 目录均不存在、无 `.api-contract.lock` → **从未运行过**。README "API 代理与对齐" 一节宣称的能力与事实不符（doc drift）。
- 当前各 app 的 `src/api/*.ts` 是同一套手工 CRUD 模板（page/list/{id}/POST/PUT/DELETE）复制产物，与后端 DDD 语义化 REST 设计（`/task/claim`、`/definition/{id}/publish`、`/instance/{id}/terminate`…）完全脱节。

**修复**：
1. 后端确认各服务 springdoc `/v3/api-docs` 可用（gen-api.mjs 已按端口 9001–9008 配好 SERVICE_MAP）；
2. 跑 `pnpm gen:api` 生成 8 份 SDK 并提交，业务 API 层改为基于 SDK 类型重写；
3. `pnpm gen:api:check` 挂入 CI（turbo pipeline + PR 门禁），从此契约漂移在提交阶段拦截。

### P0-5 前端"虚构 CRUD 模板"全面替换为真实契约

以 workflow 为例（其余 7 个 app 同模式）：

- 前端仅调用 `/api/v1/workflow/engine`（bare）、`/engine/list`、`PUT /engine`、`DELETE /engine/{id}` 等 12 个模板端点；
- 后端真实面：`FlowTaskController`（46 端点：claim/pass/reject/transfer/delegate/countersign×3/jump/freeJump/batch×4/todo/passAll…）、`FlowDefinitionController`（36）、`FlowInstanceController`（29）。

**修复**：以 P0-4 生成的 SDK 为唯一事实源，逐 app 重写 `src/api/` 层 + 对应视图层，删除虚构端点。

## 四、P2：工程化与治理建议

1. **SSE / 流式支持**：`requestClient`（axios 封装）不支持流式读取。agent `chat/stream`、`execute/stream`、userinfo `auth/events`（SSE）需要新增 `fetch`-based 流式客户端（shared-auth 统一提供，Token/TraceId 注入复用现有拦截器逻辑），并抽象统一的 SSE 重连/心跳。
2. **URL 规范统一并双向守护**：制定《API 路径规范》（`/api/v1/{service}/{resource}`，kebab-case，资源名小写复数），后端用 ArchUnit 校验 Controller 映射，前端用 ESLint 自定义规则校验 `requestClient` 调用路径风格，两端共享同一正则。
3. **契约门禁闭环**：`gen:api:check` → turbo pipeline → PR 阻塞；`.api-contract.lock` 哈希变更必须在同一 PR 中包含 SDK 再生成，杜绝"后端改了前端不知道"。
4. **适配顺序建议**（依赖关系驱动）：
   - 第一批：system（租户/审计）+ userinfo（用户/角色/菜单，修 P0-2 后）——所有页面的地基；
   - 第二批：workflow 任务办理 + 监控大盘（用户可见价值最大）；
   - 第三批：literule 调试器 + 版本/生命周期（呼应 S1–S12 与"真断点"短板）；
   - 第四批：nextwiki 搜索/批量、message 站内信、cronjob DAG 可视化、agent SSE 对话。
5. **E2E 兜底**：`e2e/` 目前为空。每完成一个服务的 API 层重写，补一条关键路径 Playwright 用例（登录 → 列表 → 办理/操作 → 断言），防止前端再次静默漂移。
6. **文档同步**：修复 README "API 代理与对齐" 与事实的偏差（SDK 未生成前不宣称契约校验已生效）；本报告建议归档至 `docs/`，与《云顶编码规范-合规审计报告》并列维护。
