## 0. 结论速览

| 维度 | 现状评级 | 一句话结论 |
|------|----------|-----------|
| 内核架构设计 | 🟢 良好 | ESM 原生路线干净（无 eval/UMD/HTML 解析），micro-runtime 接缝为未来换内核留了后路；边界声明诚实 |
| 沙箱隔离强度 | 🟡 中等 | snapshot（防意外不防恶意）+ proxy（仅 fakeWindow 数据层）+ iframe（DOM 隔离但 JS 仍在主 realm）——同源定位够用，跨信任边界不够 |
| 工程守护 | 🔴 薄弱 | CI 仅 build；README 大面积虚构命令/测试体系/git hooks；内核 153 个测试用例**无任何脚本入口** |
| 业务承载 | 🔴 空转 | 8 个子应用平均 ~2.0k LOC 壳状态（最大 userinfo 4.7k），撑不起 15k LOC 内核 + 22 公共包（48k LOC）的高级设施 |
| 过度设计倾向 | 🟡 明显 | 马尔可夫预测/四预载策略/iframe RPC/speculation-rules/css-containment 等设施先行于业务需求，且无启用率度量 |
| 文档可信度 | 🔴 失真 | README 约 12 个 script、3 类测试体系、Lefthook hooks、ADR 目录均为虚构或死链（详见 §6 Known Issues） |

**总评**：这是一个**内核工程质量高于平台成熟度、平台设施密度远高于业务密度**的项目。内核代码本身（文档化、修复可追溯、边界诚实）达到开源竞品上游水准；真正的短板不在内核，而在**守护体系断裂（CI/测试/文档三方失真）**与**设施空转（业务未跟上）**。下一阶段的正确姿势是「冻结内核新设施、修复守护链路、填充业务」，而不是继续给内核加能力。

## 2. 竞品对标

### 2.1 微前端运行时层（内核直接竞品）

| 能力 | ydsz-micro | qiankun（阿里） | wujie（腾讯） | Garfish（字节） | icestark（阿里 ice） | VS Code 扩展模型 |
|------|-----------|----------------|---------------|-----------------|---------------------|------------------|
| 加载路线 | ESM 原生 import + manifest | import-html-entry（UMD + eval） | iframe + proxy | UMD/ESM 双轨 | ESM 支持 | ESM + 进程隔离 |
| JS 隔离 | snapshot/proxy(数据层)/iframe(DOM only) | with+proxy 强隔离 | iframe 天然 realm 隔离 | 双沙箱 + vm | 弱（同源假设） | Extension Host 进程级 |
| 样式隔离 | 前缀 + CSS scope（runtime-css-scope） | scoped css | shadow DOM | scoped | 无 | DOM 隔离天然解决 |
| 依赖共享 | importmap 插件（vite-config/plugins/importmap*.ts） | externals 约定 | iframe 天然不共享 | externals | webpack externals | host 内置 |
| 预加载 | hover/idle/route/frequency 四策略 + 马尔可夫 | prefetch 简单版 | 简单 | 简单 | 简单 | activation events（声明式） |
| 热更新/版本 | version.json 轮询 + canary 灰度 | 无 | 无 | 弱 | 弱 | 扩展市场 + 自动更新 |
| 降级/容错 | 分级降级 + 重试 + error-boundary + 健康检查 | 手动 | 手动 | 弱 | 弱 | 进程崩溃自动重启 |
| 生态/工具 | Chrome DevTools 扩展（530 LOC） | 社区丰富 | 社区丰富 | 字节内部 | ice 生态 | 官方市场 + CLI |

**判断**：
1. **加载与工程链路已优于 qiankun**（无 eval/UMD/HTML 解析，SRI + CSP nonce + 带抖动重试是竞品都没有的细节），qiankun 本身已低维护，这个方向选择正确。
2. **隔离强度是结构性短板但可接受**——ESM 路线放弃 `with` 意味着永远到不了 qiankun/wujie 的 JS 隔离强度；项目注释已诚实声明。**正确策略是把「同源可信集群」写成显式架构约束（ADR），把 iframe 沙箱的安全边界（JS 仍在主 realm）写进文档**，而不是继续投入增强隔离。
3. **对 VS Code 模型的差距是维度性的**：缺声明式激活（activation events）、能力权限声明、扩展市场/注册中心服务端。当前 `activeRule` 前缀匹配是激活机制的 1/3 形态。
4. **wujie 对标结论**：若未来真出现跨团队/不可信子应用需求，正确路径是引 wujie 或自研 iframe+shadowDOM 完整方案，而不是在现有 proxy 沙箱上继续加码。

### 2.2 中后台框架层（README 自报竞品：RuoYi/pig/maku-boot/SpringBlade/JeecgBoot）

- 上述竞品的核心竞争力是**开箱即用的业务功能密度**（代码生成器、报表、工作流、租户、信创适配），而非运行时精巧度。ydsz-micro 目前恰好相反：运行时精巧、业务壳空。
- 差异化叙事（微前端 + agent-web AI 原生 + 可观测 + a11y）成立的前提是这些声称**真实存在**——当前 a11y/可观测（ADR-006 火焰图）为虚构或缺失，削弱了叙事（见 §6）。
- 信创/国密适配为竞品普遍具备、本项目空白项，若目标客户含国企/政企应为 P1。

### 2.3 大厂研发规范层

| 规范项 | 大厂通行做法 | 本项目现状 |
|--------|--------------|-----------|
| 质量门禁 | CI 强制 lint + type + test + 覆盖率，MR 阻断 | CI 仅 build；lint/type-check 仅本地手动 |
| 测试金字塔 | 单测/契约/E2E 分层且全在 CI 跑 | 仅 14 个 spec 文件；内核测试无脚本入口 |

## 3. 五维优化建议（按维度 → 可落地条目）

### 3.1 架构优化

**A1（P1）运行时与构建配置解耦**。`kernel.ts:183` 在 `registerAppsAsync` static 模式下 `await import("@ydsz/vite-config")`，把构建期配置包（含全部 Vite 插件代码）拉进浏览器产物。应将 `MICRO_APPS` 静态注册表抽为独立轻量常量包（如 `@ydsz/micro-registry`），内核与 vite-config 双向解耦。

**A2（P1）全局调试口收敛**。`kernel.ts:262` `window.__MICRO_KERNEL__ = kernelApi` 无条件暴露完整内核 API（含 `unmountApp`/`setKeepAlive`/`updateAllApps`）。改为 `import.meta.env.DEV` 条件暴露，生产环境仅暴露只读快照（供 DevTools 扩展读取），与 VS Code「扩展 API 受控表面」思路对齐。

**A3（P1）iframe 通道加固**。`iframe-bridge.ts` 中 ~8 处 `postMessage(..., '*')` 改为精确 origin（构建期注入）；接收侧补 `event.origin` 白名单校验（当前仅 `iframe-rpc.ts:79` 的 source 校验）。内网同源场景风险有限，但这是开源叙事下的基本卫生。

**A4（P2）kernel-\* 拆分粒度冻结**。`kernel.ts` 已拆出 kernel-events/health/helpers/lifecycle/managers/props/registry/router/shutdown/startup 共 11 个伴生文件，加上闭包状态访问器（`LifecycleStateAccessors`/`StartupContext` 等 7 个 context 对象）传递——拆分收益已递减（单文件最大仅 265 行），context 对象接线本身在增加理解成本。最新提交「完善文件拆分规范，防止恶意拆分」方向正确，建议按内聚度回并为 lifecycle / startup-shutdown / registry-props 3 组，并冻结继续拆分。

**A5（P2）沙箱路线显式化**。三种沙箱的真实边界（§1.2）写入一份 ADR（补上不存在的 ADR 目录），明确「同源可信集群」为架构不变量；跨信任场景的答案（引 wujie / 完整 iframe 方案）预先给出决策记录，避免后人误用。

### 3.2 功能增强

**F1（P0）守护链路修复**（详见同日合规审计报告 P0-1/2/3）：vsh 三命令修复 + check-arch glob bug + check-circular 别名解析 bug，修复后接入 CI。这是所有其他建议的前置——没有可用的看门人，规范只是纸面。

**F2（P0）内核测试接线**。给 `comm/effects/micro-kernel/package.json` 补 `"test": "vitest run"`（复用根 vitest.config.ts 的 alias 配置），使 153 个既有用例进入 `turbo test`；随后补核心路径单测：loader（manifest LRU/SRI 注入/样式清理）、sandbox（嵌套栈进出、定时器监听器清理）、scheduler（LRU/TTL 淘汰）、message-broker 超时拒绝——当前 7 个 spec 全在外围模块（canary/css/memory/broker/page-cache/predictor/registry），**核心三件套（loader/沙箱/调度器）零直接覆盖**。

**F3（P1）发布链路闭环**。内核侧 version.json + canary + `gen:registry` 已就绪，缺的是：registry 服务端落点（最简：nginx 静态 JSON + CI 自动发布）、子应用独立构建发布流水线（对齐「独立部署」承诺）、changesets 初始化（`.changeset/` 目录 + config，依赖已装）。

**F4（P1）DevTools 扩展深化**。当前 530 LOC 仅状态查看。优先级：内核事件时间线（生命周期耗时瀑布）> 沙箱/调度器实时状态 > 火焰图（成本高，且 README 引用的 ADR-006 不存在，先补 ADR 或删声称）。

**F5（P2）声明式激活演进**。把激活条件从前缀匹配演进为路由/事件/命令三类触发（对标 VS Code activation events 与 single-spa activity functions），为「子应用常驻但休眠」的细粒度激活铺路。这是 micro-runtime 接缝层的自然扩展。

### 3.3 性能提升

**P1（P1）`performance.memory` 降级路径**。`task-queue.ts:228`/`health-check.ts` 依赖非标准 Chromium API，Safari/Firefox 下内存压力调度整体失效。补 `performance.measureMemory()`（需 crossOriginIsolated）与启发式（实例数 × 估算权重）两级降级，并将降级状态暴露到健康检查报告。

**P2（P1）共享依赖单例验证**。importmap 机制已实现（`conf/vite-config/src/plugins/importmap*.ts` + `micro-shared-deps.ts`），但缺一份「8 子应用 × vue/element-plus/pinia 实例数」实测报告。运行时双实例是微前端最高频故障源（qiankun 社区 top 问题），建议在 DevTools 扩展加「共享依赖实例审计」面板一次解决检测与演示两个需求。

**P3（P2）预加载收益度量**。马尔可夫预测（route-predictor）与四预载策略目前无命中率数据。加埋点：preload 触发 → 实际消费（`recordPreloadConsumed` 已有）→ 加载耗时对比，输出月度报表。**若 frequency 策略已覆盖 90%+ 收益，应把马尔可夫预测降级为 experimental 开关**（见 §3.5）。

**P4（P2）启动体验优化**。`pnpm dev` 经 turbo-run 并行拉起 9 个 dev server，冷启动成本高（Vite ×9）。已有 `standalone` 模式（`bash/dev-standalone.mjs`）但入口埋得深；建议 `pnpm dev` 默认「主应用 + 按需拉起子应用 dev server」（内核 dev 模式已支持直接 import dev server 入口，`loader.ts:186-199`，具备条件），把 9 进程全量启动改为 opt-in。

### 3.4 体验改善

**E1（P0）README 事实化重写**。删除/修正虚构 script（§6 全清单）、死链（v4.0 说明、ADR 目录）、虚构测试体系（e2e/a11y/perf）与 Lefthook 章节。这是投入 2 小时、回报最高的一项：外部读者与未来的自己复制粘贴命令失败一次，对整个文档的信任即归零——与「以代码事实为准」的项目原则直接冲突。

**E2（P1）质量设施「要么落地要么删除」**。对 Playwright/Lighthouse/a11y 三项做一次显式决策：落地（补 config + CI job + 首批用例）或从 README 移除。当前的中间态（声称存在、实际为零）是最差选择。`test-results.json`（vitest 输出残留）应加入 .gitignore。

**E3（P1）降级 UI 实际触发验证**。error-boundary.ts（539 行）+ 三级降级 + 多语言文案同步（`micro-runtime.ts:111-114`）实现完整，但无 E2E 验证其真实触发路径。最小做法：单测模拟子应用 mount 抛错断言降级渲染；理想做法：DevTools 扩展加「故障注入」按钮，演示即测试。

**E4（P2）开发者快速上手路径**。开源前补：一条 `pnpm gen:app` → 本地注册 → 访问的 5 分钟教程（gen-app 脚手架已相当完善，缺的是文档化路径）、CONTRIBUTING.md、SECURITY.md、端口表已有（保持）、Known Issues 章节（可直接引用 §6）。

### 3.5 过度设计（削减清单）

**判定基准**：设施密度与业务密度倒挂——内核 15k LOC + 公共层 48k LOC 服务于 8 个平均 2.0k LOC 的壳应用。以下设施在当前业务负载下**缺乏启用率证据**：

| 设施 | 位置 | 处置建议 |
|------|------|----------|
| 马尔可夫路由预测 | route-predictor*.ts（~630 LOC + 757 行测试） | 保留实现，加命中率埋点；两迭代内无收益证据 → experimental 开关默认关 |
| iframe 沙箱 + RPC 桥 | iframe-*.ts（~1000 LOC） | 确认是否有子应用实际配置 `sandbox: 'iframe'`；无使用者 → 归档为实验特性并在文档声明 |
| speculation-rules / css-containment / hover-feedback | 各自独立模块 | 统一挂到 `@core/feature-flags` 开关后（包已存在，接线即可），默认关闭 |
| canary 三级白名单灰度 | canary-*.ts（~900 LOC） | 内核侧保留；服务端 registry 未落地前，灰度实际不可用——优先补 F3 而非继续增强 canary |
| Chrome DevTools 扩展 | chrome/（530 LOC） | 保留（差异化卖点），但与 F4 合并投入，不做孤立功能 |
| 22 个公共包 | comm/ | 做一次消费关系审计：无 `workspace:*` 消费者的包冻结或合并（尤其 utils 与 @core/shared 的职责边界） |

**总原则**：不建议删除（平台型项目的设施先行有合理性），但每项设施必须满足三选一——有启用率数据 / 有 E2E 演示 / 标注 experimental 默认关闭。**同时冻结内核新设施 1–2 个迭代，把产能转向业务填充**（userinfo → system → workflow 顺序），避免重蹈「前后端能力不匹配」覆辙。

## 5. 值得保持的优点（对标中的正向资产）

1. **诚实的边界声明**：proxy-sandbox 开头即承认 ESM 无 with 的结构性局限、snapshot 自认「不防恶意代码」——绝大多数开源竞品的文档做不到这种坦率，这是可信度资产，保持。
2. **修复可追溯**：v3.1 嵌套沙箱栈修复、P0-A2 闭包状态收敛等注释带根因与影响范围，代码即变更史。
3. **micro-runtime 接缝**：ports & adapters 式接口层为未来替换内核（或被 wujie 类方案替换）预留了低成本切换点，这是对「自研可控」的正确工程化表达。
4. **加载器细节**：SRI + CSP nonce + LRU manifest + 带抖动指数退避，超过 qiankun/wujie 同位置的实现密度。
5. **统一构建约定**：vite-config 共享配置 + manifest 约定 + gen:app/gen:nginx/gen:registry 脚手架链，同源集群工程一致性好。
