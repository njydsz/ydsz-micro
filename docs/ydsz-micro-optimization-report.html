核心结论：该项目拥有业界少见的自研 ESM 原生微前端内核（三层沙箱、金丝雀分流、马尔可夫链预加载），架构设计水平远超主流 qiankun/wujie 方案。但存在两个系统性短板：(1) 测试覆盖率极低（7.6%），12个核心包零测试，已达生产事故风险级别；(2) 大量 boilerplate 代码（10+文件/子应用×8=80+文件）纯为转发层，且在8个子应用中机械重复。短期应聚焦修复编译阻断问题与测试欠债，中期应消除重复并统一状态管理架构。

一、架构优化

1.1 bootstrap.ts 单体函数拆分（P0）

P0 架构main/src/bootstrap.ts 406行单一函数，违反单一职责原则

现状：一个函数内耦合了日志初始化、组件适配器、功能开关、Vue应用创建、5个全局指令注册、i18n、Pinia Store、路由守卫、动效、监控、灰度、微前端运行时（~150行独立逻辑）、路由预加载、DevTools Bridge、会话超时、跨标签同步共18项职责。

对标：大厂微前端主应用普遍采用插件化 bootstrap（如字节跳动 Garfish 的 plugin system、阿里 qiankun 的生命周期钩子），每个插件独立可测试。

建议方案：

// 拆分为独立 setup 模块，bootstrap.ts 仅保留编排逻辑
import { setupLogger } from './setup/logger';
import { setupPlugins } from './setup/plugins';
import { setupMicroRuntime } from './setup/micro-runtime';
import { setupMonitoring } from './setup/monitoring';
import { setupRouterGuards } from './setup/router-guards';

async function bootstrap() {
  setupLogger();
  await setupPlugins(app);       // 组件适配器、指令、i18n、动效、Pinia
  await setupRouterGuards(app);   // 路由守卫注册
  await setupMicroRuntime(app);   // 微前端运行时、预加载策略
  setupMonitoring(app);           // Sentry、Web Vitals、DevTools
  app.mount('#app');
}

1.2 notificationStore 非 Pinia 实现（P0）

P0 架构store/notification.ts 使用 class-based singleton，与 Pinia 架构不一致

现状：238行的 notificationStore 使用手动 ref()/reactive() 管理状态，非 Pinia defineStore。无法享受 Pinia DevTools 调试、$reset()、$subscribe 等内置能力。

对标：Vue 3 官方推荐 Pinia 为唯一状态管理方案（2026 年 Pinia 已是 Vue 生态的事实标准），Vuex 已进入维护模式。

建议方案：

// 重构为 Pinia Setup Store 风格
export const useNotificationStore = defineStore('notification', () => {
  const notifications = ref<NotificationItem[]>([]);
  const unreadCount = ref(0);
  const wsConnected = ref(false);

  function connectWs(token: string) { /* WebSocket 逻辑 */ }
  function handleWsMessage(msg: any) { /* 消息路由 */ }

  return { notifications, unreadCount, wsConnected, connectWs, /* ... */ };
});

1.4 @YDSZ-core/menu-ui 反向依赖（P1）

P1 架构底层 UI 组件包依赖高层微前端内核包，违反依赖方向

现状：@YDSZ-core/menu-ui（UI 组件层）→ @ydsz/micro-kernel（业务效果层），这是反向依赖。底层包不应感知上层业务包的存在。

对标：依赖反转原则（DIP）：高层模块不应依赖低层模块，两者都应依赖抽象。

建议：在 @YDSZ-core/typings 中定义 MenuIntegration 接口，menu-ui 依赖接口而非具体实现，micro-kernel 实现该接口并在主应用中注入。

1.5 共享依赖版本管理（P1）

P1 架构pnpm catalog 与实际 package.json 版本不一致

现状：

  • catalog 中 element-plus 版本为 ^2.10.2，shared-business 硬编码 ^2.7.0
  • shared-auth 中 openapi-fetch 版本 ^0.17.0 未使用 catalog
  • 多个包未通过 catalog 统一管理版本，存在版本漂移风险

建议：所有内部包统一使用 "element-plus": "catalog:" 引用，通过 Renovate/Dependabot 自动化版本管理。

1.6 standalone 开发模式推广（P2）

P2 架构仅 userinfo-web 支持独立开发，其余7个子应用必须依赖主应用

现状：userinfo-web 通过 standalone-main.ts + Mock 层实现了完整的独立开发能力，但其他7个子应用缺失此能力。这导致开发时必须启动主应用，降低了开发效率。

对标：Module Federation 生态中，每个 remote 应用天然支持独立开发；qiankun/wujie 社区最佳实践也推荐子应用独立可运行。

建议：将 standalone 模式模板化到 @ydsz/shared-auth（如 createStandaloneApp），各子应用只需提供 Mock 处理器即可独立运行。

三、性能提升

3.1 shareStrategy 策略普及（P1）

P1 性能8个子应用中仅2个配置了 shareStrategy，其余6个使用默认 all

现状分析：

应用shareStrategy外置依赖首次加载预估
mainall全量（Vue/Pinia/VueRouter/ElementPlus/ECharts/Dayjs）~
agent-weball（默认）全量较大
message-weball（默认）全量较大
system-weball（默认）全量较小（配置类页面）
userinfo-weball（默认）全量较大
nextwiki-weball（默认）全量中等
cronjob-webcore-ui框架 + ElementPlus/VXE-Table优化中
literule-webcore仅 Vue/Pinia/VueRouter最激进优化
workflow-weball（默认）全量较大

建议：分析各应用实际依赖，配置合适的 shareStrategy。agent-web、message-web 如不使用 ECharts 可设为 core-ui；system-web（纯配置页）可激进设为 core。

3.2 虚拟列表 & 大列表优化（P2）

P2 性能CRUD 列表页使用 h() 函数渲染操作列，大量数据时影响性能

现状：agent-web 等子应用的列表页中，gridOptions 通过 h() 函数渲染操作按钮列。当列表数据超过 500 条时，每个操作列的 VNode 创建会产生可感知的延迟。

对标：Vue 3 最佳实践推荐使用虚拟滚动（@tanstack/vue-virtual）处理长列表，配合 VXE-Table 的虚拟滚动模式。

建议：在 useCrudTable composable 中集成 VXE-Table 的虚拟滚动配置，默认启用 scroll-y 虚拟渲染。操作列改用 slots 模式（编译时优化）替代 h() 函数。

3.3 WebSocket Token 安全（P2）

P2 性能/安全WebSocket URL 中 Token 明文传递

现状：const wsUrl = `${protocol}//${host}/ws/notification?token=${token}`，Token 通过 query string 明文传递，可能被中间代理/日志记录。

建议：WebSocket 连接建立后，通过首帧握手消息传递 Token（参考 Socket.IO auth 机制），或使用 HttpOnly Cookie 自动携带。

3.4 懒加载深度优化（P2）

P2 性能部分重型依赖未做懒加载拆分

建议：

  • ECharts 改为 defineAsyncComponent 按图表类型懒加载（项目中已有但未在所有使用场景铺开）
  • VXE-Table 的非核心功能（导出/导入/打印）单独拆 chunk
  • monaco-editor（如 workflow-web 的 BPMN 编辑器）独立异步加载，不在首屏打包

四、体验改善

3.1 command-palette.vue 事件注销 Bug（P0）

P0 体验removeEventListener 传入新空函数引用，无法移除原监听器

现状：

// command-palette.vue — 错误代码
onUnmounted(() => {
  window.removeEventListener('YDSZ:register-commands', () => {});  // 新函数引用！
  window.removeEventListener('YDSZ:unregister-commands', () => {}); // 无法移除
});

影响：每次进入/离开 Command Palette 页面都会累积事件监听器，可能导致内存泄漏。

修复：

// 正确做法：保存回调引用
const handleRegister = (e: CustomEvent) => { /* ... */ };
onMounted(() => window.addEventListener('YDSZ:register-commands', handleRegister));
onUnmounted(() => window.removeEventListener('YDSZ:register-commands', handleRegister));

3.2 死代码清理（P1）

P1 体验多处未使用的 import 和 void 标记的死代码
  • global-search.vue：定义了 function handler(e) 用于 cmd+k 快捷键，又通过 void handler 标记为未使用，整段死代码
  • command-palette.vue：未使用的 import { getPreloadManager }
  • basic.vue：未使用的 import type { NotificationItem }

建议：配置 ESLint 规则 no-unused-vars 为 error 级别，CI 中阻断。

3.3 SubAppContainer 组件拆分（P1）

P1 体验subapp/index.vue 498行，职责过重

现状：单个组件包含：生命周期管理、7阶段状态映射、骨架屏解析、无障碍公告、焦点管理、错误遮罩、进度条等所有逻辑。

建议：提取 composable：

// 拆分为可独立测试的 composable
import { useSubAppLifecycle } from './composables/use-lifecycle';
import { useSkeletonResolver } from './composables/use-skeleton';
import { useA11yAnnouncements } from './composables/use-a11y';
import { useSubAppFocus } from './composables/use-focus';

3.4 microRuntime 导出不可变（P1）

P1 体验microRuntime 使用 let 导出，外部可意外修改

现状：export let microRuntime: ReturnType<typeof createRuntime> | null = null;

建议：改为 const + getter 模式或使用 readonly ref：

let _microRuntime: ReturnType<typeof createRuntime> | null = null;
export const getMicroRuntime = () => _microRuntime;
// 或提供只读代理

3.5 无障碍与 i18n 覆盖（P2）

P2 体验组件无障碍标签不完整，部分文案硬编码

建议：为所有交互组件添加 aria-label（按钮、链接、表单控件），确保 screen reader 可用。硬编码的中文文案迁移到 i18n 文件。

五、过度设计简化

5.1 薄包装层合并（P1）

P1 简化@YDSZ-core/* 与 @ydsz/* 双层命名空间中存在薄包装层
包装包文件数实际内容建议
@ydsz/preferences1 TS仅 defineOverridesPreferences 函数 + re-export合并到 @YDSZ-core/preferences 或 @ydsz/stores
@ydsz/constants2 TSre-export @YDSZ-core/shared + 1个自有文件合并，减少包数量

总体建议：在不破坏架构清晰度的前提下，将薄包装层（核心逻辑不超过 50 行的包）合并，将 32 个 comm 包精简到 ~25 个。

5.2 TypeScript 路径映射简化（P2）

P2 简化tsconfig.paths.json 手动维护 48 个路径映射

现状：手动维护 48 个路径映射，存在大小写不一致（@YDSZ-core vs @ydsz），部分映射指向 src/index.ts（dev 直出）而非 dist/（生产）。

建议：使用 Turborepo 的自动路径解析 + pnpm workspace 协议，减少手动路径映射。或使用 unplugin-auto-import 自动处理内部包引用。

5.3 docker-compose 端口收敛（P1）

P1 简化/安全docker-compose 暴露 9 个 Java 微服务端口到主机

现状：所有后端服务（9000-9008）端口均映射到主机网络，存在安全隐患。生产环境应仅暴露 Gateway（9000），其他服务通过内部 Docker 网络通信。

建议：

# 仅暴露 gateway 端口，其余服务移除 ports 映射
services:
  gateway:
    ports:
      - "9000:9000"
  auth-service:
    # ports 移除，通过内部网络访问
    networks:
      - ydsz-net

5.4 useSearchProvider 的 setTimeout 注册（P2）

P2 简化use-global-search.ts 中 100ms setTimeout 依赖时序假设

现状：setTimeout(() => registerSearchProvider(appName, provider), 100) 依赖子应用在 100ms 内挂载完成。

建议：改为事件驱动——子应用 mount 完成时触发 YDSZ:search-provider-ready 事件，主应用监听后注册。

5.5 废弃构建配置清理（P2）

P2 简化部分包的 build 脚本被注释，混用 vite build 与 unbuild
  • @YDSZ-core/preferences 的 build 脚本被注释（"#build": "pnpm unbuild"）
  • @YDSZ-core/design 使用 vite build，其他包使用 unbuild，构建工具不统一

建议：统一所有 comm 包的构建工具为 unbuild（更适合纯 JS/TS 库），或明确各包的构建策略。
