## 1. 核心问题详述（按优先级）

### 🔴 P0-1：规范守护 CLI 整体不可用

`bash/vsh/package.json` 声明了 `commander@^12` 和 `@typescript-eslint/typescript-estree@^8`，
但 `bash/vsh/node_modules/` 实际只装了 `@ydsz/cac`、`circular-dependency-scanner`、`depcheck`、`publint`。

直接后果：
- `pnpm check:dep` → `ERR_MODULE_NOT_FOUND: commander`
- `pnpm vsh:check-arch` → 同上
- `pnpm vsh:check-circular` → 同上（且即便装上，AST 解析器也缺失）

根因推测：`bash/vsh` 作为 workspace 子包，`node_modules` 未随根 `pnpm install` 同步安装其声明的 dependencies（可能漏提交 lock 或未执行 `-r` 安装）。

**修复路径**：
1. 在 `bash/vsh` 下补装 `commander` 与 `@typescript-eslint/typescript-estree`（确认版本与 catalog 对齐）。
2. 在根 `package.json` 的 `postinstall` 或 CI 中确保 `bash/vsh` 依赖被安装。
3. 修复后把三个命令纳入 `pnpm check` 综合检查（当前 `pnpm check` 是否真的调用它们需确认）。

### 🔴 P0-2：`check-arch` 架构守护存在逻辑缺陷

`bash/vsh/src/check-arch/index.ts` 的两个实现问题：

1. **`matchesGlob` 退化**：`from: ['apps/*']` 调用 `normalizedPattern.replace(/\*/g, '')` → 变成 `apps/`，再 `includes('apps/')`。
   这意味着 `apps/userinfo-web/src/x.ts` 会命中，但 `comm/utils/src/x.ts` 也会被 `utils/` 之类误命中；
   `*` 被当空串，无法区分 `apps/a` 与 `apps/anything/deep`。**规则精度严重不足**。
2. **导入判定错误**：`line.includes(toPattern.replace('/', ''))` 把 `comm/effects/` 变成 `commEffects`
   （只删第一个 `/`），然后用 `includes('commEffects')` 匹配源码行——正常 import 语句写的是
   `comm/effects/request`，根本不会包含 `commEffects`，**导致大量违规被漏报**。

后果：架构分层约束（如 `no-app-direct-import-effects`、`utils-no-effects`）形同虚设。

**修复路径**：
- 用真正的 glob/minimatch 匹配路径，或对 `from` 用前缀+层级判断。
- 导入判定应基于解析后的 import specifier（去掉引号、处理别名映射），而非字符串 includes。

### 🔴 P0-3：`check-circular` 别名解析错误，循环检测漏报

`resolveImport` 逻辑：
```
if (importPath.startsWith('.')) return resolve(fileDir, importPath);
if (importPath.startsWith('@')) return resolve(rootDir, 'src', importPath.replace(/^@[^/]+\//, ''));
return null;  // #/ 别名直接被丢弃
```
问题：
- 项目别名是 `@ydsz/...`、`@YDSZ-core/...` 以及 **`#/`**（vite 配置中的 `@/`/`#/` 风格）。
  `#/` 开头的 import **直接 `return null`**，不参与图构建 → 凡经由 `#/` 别名形成的依赖边全部丢失。
- `@` 分支硬编码 `resolve(rootDir, 'src', ...)`，但子应用的 `#/` 指向各 app 的 `src`，而 `@ydsz/*`
  指向 `comm/*/src`（需在 tsconfig.paths 中查表），简单拼接会解析到错误路径。

后果：循环依赖检测对主路径（占引用量 90% 的 `#/` 别名）**完全失明**，规范 18.x 的"循环依赖零容忍"无法落地。

**修复路径**：
- 复用 `tsconfig.paths.json` 的 paths 映射做别名解析（而不是手写正则）。
- 支持 `#/` 别名（解析到各包 `src`）。
- 建议直接接入 `circular-dependency-scanner`（已在 node_modules 中，但未在代码里使用）。

### 🟡 P1-1：console 未收敛到统一 logger

扫描发现 comm 组件层大量裸 `console.*`（节选）：
- `comm/effects/common-ui/src/components/error-boundary.vue:84` `console.error('[ErrorBoundary]...')`
- `comm/effects/common-ui/src/components/error-feedback.vue:140/153`
- `comm/effects/common-ui/src/components/captcha/point-selection-captcha/index.vue`（6 处）
- `comm/effects/layouts/.../check-updates.vue:63`、`comm/@core/ui-kit/form-ui/.../form.vue:141` 等

规范 **14.5【强制】**：生产环境禁止 `console.log`，必须使用 `@ydsz/monitor` 的 `logger`。
现状：`comm/@core/base/shared/src/utils/logger.ts` 已实现统一 logger，但组件层未引用，下沉不到位。

**修复路径**：
- 在 ESLint 增加 `no-console` 规则（`allow: ['warn']` 或全禁，由规范定级）。
- 提供 codemod 将裸 console 替换为 `logger.*`，并对 error-boundary/error-feedback 这类全局兜底层明确"上报 + logger"双写。

### 🟡 P1-2：comm/effects 基础设施层 any 超出豁免范围

规范 **3.1【强制·豁免条款】** 仅豁免 `comm/@core/ui-kit/shadcn-ui`（CLI 生成件）。
但扫描到 `comm/effects/` 下约 33 处 `any`，集中在：
- `comm/effects/request/`（preset-interceptors、cache-adapter）
- `comm/effects/monitor/`（web-vitals、sentry、setup）
- `comm/effects/micro-kernel/`（kernel、proxy-sandbox、iframe-* 等）
- `comm/effects/shared-auth/`、`comm/effects/common-ui/`（json-viewer、api-component 等）

这些是核心基础设施，类型收窄价值高。现状多数为 `any` 透传 axios/第三方回调，缺乏收窄或合规注释。

**修复路径**：
- 对 request/monitor 这类"与外部 SDK 接壤"的边界，用 `unknown` + 类型守卫或 `// 非标准 API 收窄` 注释闭环（规范已留口子）。
- 对 micro-kernel 内部通信（postMessage/RPC）定义明确消息类型，消除 `any`。

### 🟡 P1-3：文档漂移

`README.md` 引用了：
- `docs/v4.0-优化设施说明.md` → **不存在**（ls docs/ 仅 `云顶编码规范.md`）
- `docs/decisions/`（ADR-003 等）→ **目录不存在**

规范 18.x 与 Roadmap 均强调文档对齐大厂标准（架构图、Known Issues、ADR）。现状 README 指向死链。

**修复路径**：
- 补建 `docs/v4.0-优化设施说明.md` 与 `docs/decisions/`，至少补齐 README 已承诺的 ADR-001~006。
- 或修正 README 链接（若文档计划变更）。

### 🟡 P1-4：`check-dep` 检查深度不足

`bash/vsh/src/check-dep/index.ts` 现状只做两件事：
1. `forbiddenPackages` 是否命中（列表为空 → 永远不触发）。
2. `@ydsz/` 内部包是否用 `workspace:*` 协议。

**未覆盖**规范 18.x 真正关心的：
- 业务代码是否绕过 `@ydsz/request` 直用 `axios`/`fetch`（已在源码层验证 apps 达标，但工具未守护）。
- 新增第三方依赖的许可证合规（`allowedLicenses` 定义了但没真正比对 license 字段）。
- 依赖是否都在 `pnpm-workspace.yaml` 的 catalog 中锁版本（"最小化外部依赖"的硬性抓手）。

**修复路径**：扩展 `check-dep` —— 解析每个包的真实依赖树，比对 catalog；扫描源码 import 是否被允许的边界包白名单约束。

## 3. 下一步优化完善建议（可执行清单）

### P0（守护链修复，阻塞所有后续合规保证）
1. **修复 vsh 依赖安装**：补装 `commander` + `@typescript-eslint/typescript-estree`，确保 `check-dep/check-arch/check-circular` 可运行；纳入 CI `pre-push`。
2. **重写 `check-arch` 匹配逻辑**：引入真实 glob 匹配 + import specifier 解析（非字符串 includes）。
3. **重写 `check-circular` 别名解析**：复用 `tsconfig.paths.json` + 支持 `#/`，或直接改用已安装的 `circular-dependency-scanner`。

### P1（代码收敛与文档）
4. **console 收敛**：ESLint `no-console` 规则 + codemod 替换为 `@ydsz/monitor` logger；error-boundary/error-feedback 保持"logger + 上报"双写。
5. **any 收窄**：对 `comm/effects/{request,monitor,micro-kernel,shared-auth}` 的 any 做类型守卫/合规注释闭环（对齐 3.1 豁免条款精神）。
6. **消除文档漂移**：补 `docs/v4.0-优化设施说明.md` 与 `docs/decisions/`（ADR-001~006），或修正 README 死链。
7. **深化 `check-dep`**：比对 catalog 锁版本 + 扫描源码 import 边界白名单 + 真正校验 license。

### P2（增强与对标）
8. **补 arch 规则**：把"子应用必须导出标准生命周期""业务代码禁直用 axios"落成 `check-arch` 的机器可执行规则（而非仅靠 README 约定）。
9. **测试覆盖率落地校验**：`vitest.config.ts` 已设 perFile 阈值（branch/func 70%、line/state 80%），但需确认 `pnpm test:coverage:check` 真实跑通且未因依赖缺失失效（参考 P0 同类风险）。
10. **信创适配**：规范/Roadmap 均提及国密、达梦/人大金仓——前端侧目前无对应适配层，建议在 Roadmap 中给出前端可落地的点（如 crypto 抽象、驱动无关的数据访问封装）。
11. **Changesets 发布配置**：Roadmap 标记待办（`.changeset/` 未初始化），影响共享包版本治理。
